## 7. 数据表创建与字段变更

本节的操作分两类：

- **纯 SQLite 的元数据变更**（改 label / description / required、状态迁移、密钥轮换）：
  包在 `BEGIN IMMEDIATE` 事务内，不需要 `serial()`。
- **跨存储操作**（建表、加字段、改名、删字段）：既要动 ClickHouse DDL（`ch_meta` 账户）
  又要动 SQLite 元数据，两者无法同处一个事务，因此全部在 `serial()` 串行队列内执行，
  并依赖 7.4 的 reconcile 兜底中间态。

### 7.1 创建数据表

1. Node 生成 `projectId`、`physical_name` 和 `ingestSecret`（32 字节随机，Base64URL）。
2. 向 SQLite `collect_tables` 插入一行 `status = 'creating'`。
3. 使用服务端生成且经过校验的字段名创建 ClickHouse 物理表。
4. 成功后把该行 `UPDATE` 为 `status = 'active'`。
5. 返回 `projectId` 与 `ingestSecret`。**上报示例代码由管理后台前端拼装展示**
   （按 8.1.3 的模板，见 10.3），服务端不返回代码字符串。
6. 失败时把该行置为 `status = 'failed'`，允许管理员幂等重试。

Node 不能使用用户输入的项目名称作为物理表名。

### 7.2 新增字段

```sql
ALTER TABLE data.collect_a8f31c
ADD COLUMN IF NOT EXISTS `country` LowCardinality(Nullable(String));
```

物理类型按 6.6 的映射表由 `type` 生成，不接受调用方指定。

执行顺序：

1. 校验字段定义：Key 正则（5.2）、`type` 属于 5.4 的六种、`options` 与 `type` 相容
   （`enum` 必须带至少一个 `active` 选项，其余类型必须不带，违反返回 `INVALID_FIELD_VALUE`）。
2. 执行 `ADD COLUMN IF NOT EXISTS`。
3. 在一个 SQLite 事务内先按 5.2 清掉该 Key 的 `dropped` / `renamed` 墓碑（**只删元数据行，
   不发任何 DDL**），再向 `collect_fields` 插入一行 `status = 'active'`、
   向 `collect_field_options` 批量插入选项行（非 `enum` 则不插），
   并递增 `collect_tables.schema_version`。剩下能撞上主键约束的只有两种情况，捕获后区分返回：
   Key 正被占用（`active`）→ `FIELD_KEY_EXISTS`，Key 已软废弃（`deprecated`）→ `FIELD_KEY_RETIRED`。
   这两种情况下物理列本来就在，ClickHouse 侧因为用了 `IF NOT EXISTS` 而确实无副作用。
4. 清除 Node 进程内对应表结构缓存。

**墓碑清理必须连选项一起清。** 一个 Key 曾经是 `enum`、被物理删除后又以 `string` 重建时，
`collect_field_options` 里那批旧选项行会因为 `(project_id, field_key)` 相同而复活成新字段的值域。
第 3 步删墓碑行时 `ON DELETE CASCADE` 会带走它们（见 6.4.1），这依赖 `PRAGMA foreign_keys = ON`
真的开着——这是 3.3.2 那四条 PRAGMA 里最容易被忽略、后果又最隐蔽的一条。

该操作设计为幂等，DDL 成功但元数据更新失败时可以安全重试。

### 7.3 修改、废弃与删除字段

**修改 label / description / required**（无数据影响）：

`UPDATE collect_fields SET ...` 更新该行，不触碰物理表。前两者 `schema_version` 不变，`required` 变更加一。

**重命名字段 Key**（无数据影响）：

```sql
ALTER TABLE data.collect_a8f31c RENAME COLUMN `country` TO `country_code`;
```

1. 校验新 Key 符合 5.2 规则。
2. 执行 `RENAME COLUMN`。该语句**没有 `IF EXISTS`**，因此执行前先查一次 `system.columns`：
   旧列已不存在、而新列已存在时，说明上一次的 DDL 已经成功、只是 SQLite 侧中断了，
   此时跳过 DDL 直接往下补元数据。这让「再点一次重命名」能够收尾，
   与 7.5 删表中断后重试收尾的路径同构。
3. 在一个 SQLite 事务内写两行：旧 Key 行更新为 `status = 'renamed'`、`renamed_to = <新 Key>`；
   新 Key 先按 5.2 清掉可能存在的 `dropped` / `renamed` 墓碑，再插入一行 `status = 'active'`，
   继承原有的 label / type / required / description。新 Key 若被 `active` / `deprecated` 占用，
   第 2 步的 `RENAME COLUMN` 就已经因为目标列存在而失败（返回 `FIELD_KEY_EXISTS` /
   `FIELD_KEY_RETIRED`）；元数据侧仍保留同样的约束兜底，冲突时回滚并把物理列改回原名。
   `schema_version` 加一。
4. 清除缓存。
5. 响应中返回提示：前端上报代码需同步改用新 Key，否则旧 Key 的上报会被拒绝。

**修改枚举选项**（无数据影响，纯 SQLite）：

`PUT .../fields/:fieldKey/options` 提交**完整的选项列表**，数组顺序即 `sort_order`。
服务端在一个 `BEGIN IMMEDIATE` 事务内按 `value` 做 diff：

1. 提交列表里的新 `value` → `INSERT`。
2. 已存在的 `value` → `UPDATE` 其 `label` / `status` / `sort_order`（`value` 本身永不更新）。
3. **现存但未出现在提交列表里的 `value` → 整个请求失败**，返回 `INVALID_FIELD_VALUE`（400），
   `message` 里列出缺了哪些，并写明「要停用请带 `status: "disabled"` 一并提交」。
4. 按 5.3 决定版本：本次有新增选项或有 `status` 变化 → `schema_version` 加一；
   只改了 `label` / 顺序 → 版本不变。
5. 清除缓存。

第 3 条是这个接口的关键。全量提交本来最自然的语义是「没提交的就删掉」，但**选项不能删**（见 5.5），
而「没提交的就自动停用」同样危险：前端少传一项就会静默关掉一个还在用的选项，
上报侧当场开始报 `INVALID_FIELD_VALUE`，而操作者以为自己只是改了个 `label`。
要求显式带全，是让「停用」这件事必须被明确写出来。

字段不是 `enum` 时调用本接口返回 `INVALID_FIELD_VALUE`，`message` 说明该字段的实际类型。

**`string` ⇄ `enum` 转换**（数据完整保留，跨存储操作）：

```sql
-- string → enum
ALTER TABLE data.collect_a8f31c
MODIFY COLUMN `login_method` LowCardinality(Nullable(String));

-- enum → string
ALTER TABLE data.collect_a8f31c
MODIFY COLUMN `login_method` Nullable(String);
```

这是**全系统唯一提供的类型变更接口**（`POST .../fields/:fieldKey/retype`，见 15.4），
只接受这两个方向，其余任何 `from → to` 组合返回 `INVALID_FIELD_TYPE`（400）。前置状态：仅 `active`。

执行顺序（在 `serial()` 内）：

1. 校验方向合法，且 `string → enum` 时带了至少一个 `active` 选项、`enum → string` 时没带 `options`。
2. 执行 `MODIFY COLUMN`。**不加 `mutations_sync`，让它异步跑**（理由见下）。
3. 在一个 SQLite 事务内更新 `collect_fields.type`；
   `string → enum` 插入选项行，`enum → string` 删光该字段的选项行。`schema_version` 加一。
4. 清除缓存。
5. 响应带 `message`：`string → enum` 提示「历史数据中不在选项内的值仍可查询与分组，
   但新上报会被拒绝，请先确认前端发的值都已登记」。

**历史值不受新值域约束。** `string → enum` 只改变**今后**的上报校验，一个字节的历史数据都不动。
因此转换后完全可能查到不在 `options` 内的历史值——这是刻意的：那些数据是真实发生过的，
把它们藏起来才是错的。管理后台应当在转换弹窗里先用统计接口拉一次该字段的 Top 值
（`dimension.kind = "field"`，见 9.4），让操作者一键把它们登记成选项，而不是转换完再来惊讶。

**为什么这条 `retype` 可以有，而跨类型族的不行。** 差别不在「是不是改类型」，
而在**这条 DDL 会不会失败、会不会改变值**：

- `MODIFY COLUMN` 在 `String` 与 `LowCardinality(String)` 之间是无损重写，任何历史值都不会
  转换失败、不会截断、不会变形（理由见 5.3 最后一段）。
- 因此它是**一条** DDL，而不是「`DROP` + `ADD`」两条。跨类型族之所以不做成一条路由，
  正是因为两条 DDL 之间崩溃会留下「列已删、新列未建，而元数据仍是旧类型」的中间态，
  reconcile 会照旧类型补出一根空列，操作静默回到原点。
- 这条转换的崩溃中间态则**无害**：DDL 成功而 SQLite 未更新时，物理列已是新编码、元数据仍是旧类型，
  两边存的值完全一样，读写都正常，唯一的差别是校验强度还没切换。7.4 的物理类型漂移检查会发现
  并补齐，操作者重试一次也能收尾。

`MODIFY COLUMN` 换编码需要重写该列的数据，是一次后台 mutation，大表上不是瞬时的。
接口**不等待 mutation 完成**（不设 `mutations_sync`）就返回：等待会让请求挂到超时，
而这段时间里该列的读写本来就是正常的——ClickHouse 会在 mutation 完成前按旧编码读、新编码写，
对调用方不可见。需要观察进度时查 `system.mutations`。

**其余类型之间的转换**（不提供入口，需自行删除后重建）：

**除 `string` ⇄ `enum` 外，字段类型不可修改。** 服务端没有其它改类型路径，管理后台也没有对应入口。
需要在其它类型之间切换时，由操作者自行依次执行两个各自独立的已有操作：

1. **物理删除该字段**（见本节下面那条，`confirm` 等于 `fieldKey`）——物理列被 `DROP`，
   元数据行置 `dropped` 墓碑。
2. **新增同名字段**（见 7.2）——Key 不变、`type` 换成新的。按 5.2，`dropped` 的 Key 允许复用，
   7.2 第 2 步会先清掉那行墓碑再插入新的 `active` 行。

前端只在字段配置页给一句说明：**「`string` 与 `enum` 之间可以直接转换且不丢数据；
换成其它类型必须先删除该列，再新建同名列」**（见 10.3），
**不为这条路径提供任何一键改类型的按钮，也不做两步之间的自动串联**。

物理效果与 `DROP COLUMN` + `ADD COLUMN`（同名，新类型）一致：

```sql
ALTER TABLE data.collect_a8f31c DROP COLUMN IF EXISTS `remember_me`;
ALTER TABLE data.collect_a8f31c ADD  COLUMN IF NOT EXISTS `remember_me` Nullable(String);
```

差别只在元数据：`schema_version` 加二（两步各加一），该行的 `created_at` 是重建时刻而非首次创建时刻，
label / required / description 也不会自动继承，需要在新建时重新填写。
两步之间该 Key 的上报会被拒为 `UNKNOWN_FIELD`——这段窗口有多长由操作者自己掌握。

**为什么这些方向不能也做成一条 `retype` 路由。** 单条路由要在同一个 `serial()` 内先发两条 DDL、再写元数据。
若在 `DROP` 成功、`ADD` 失败之间崩溃，SQLite 里的 `type` 还停在旧值，7.4 的 reconcile 会照
**旧类型**补出一根空列——数据丢了、类型没改，操作静默回到原点，而操作者以为已经改成功。
要修就得把元数据写在 DDL 之前，可那样又会在崩溃后留下「元数据说新类型、物理列还是旧类型」的错配。
拆成两步则不存在这种中间态：物理删除与新增字段各自都是 7.3 / 7.2 已经定义好的、
能被 7.4 收敛的独立操作，中途失败最坏停在「字段已删、新字段未建」，操作者补做第二步即可收尾。
让操作者手动走完这两步，也比一个按钮背地里连发两个高危请求更诚实——删完之后建不建、
什么时候建、建成什么类型，全都还在操作者手里。

**软废弃**（默认，保留数据）：

- `collect_fields` 中该行更新为 `status = 'deprecated'`。
- 上传接口拒绝继续提交该字段（`DEPRECATED_FIELD`）。
- 新建查询默认隐藏该字段，历史查询可以显式选择——载体是 9.1 的 `includeFields`，
  以及 `filter` 条件与 `statistics` 的 `dimension.field` / `measure.field` / `axis` 里直接写出该 Key。
- ClickHouse 物理列和历史数据保留。
- **软废弃是可退出的中间态**：想彻底清掉这一列、或想把这个 Key 换成别的类型重建，
  对它执行下面的物理删除即可（见 5.2）。

**物理删除**（高危，数据不可恢复）：

```sql
ALTER TABLE data.collect_a8f31c DROP COLUMN IF EXISTS `country`;
```

**前置状态**：该字段必须是 `active` 或 `deprecated`。这两种状态下物理列都还在，`DROP COLUMN`
才有实际效果；`dropped` / `renamed` 名下已经没有物理列了，返回 `FIELD_NOT_FOUND`。
注意这里与「改 label / description / required」「重命名」「软废弃」三条不同——那三条只接受
`active`（对一个已经废弃的字段改必填规则或再废弃一次没有意义），删除则两种状态都接受。

1. 请求体必须携带 `confirm` 字段，其值等于待删除的 `fieldKey`，否则返回 `CONFIRMATION_REQUIRED`。
2. 执行 `DROP COLUMN IF EXISTS`。
3. `collect_fields` 中该行更新为 `status = 'dropped'`（记录行保留，作为 tombstone），递增 Schema 版本。
4. 清除缓存。

该行保留为 `dropped` 墓碑，用于阻挡「同一张表内 Key 被无意复用」。
按 5.2，操作者可以主动用同名 Key 重新建一个字段：那会先删掉这行墓碑，再建出一列全新的空列，
被删除的历史数据不会、也不可能因此回来。

如因敏感信息或法律要求必须清理行级数据，见 14.2 的运维流程。

### 7.4 启动期状态收敛（reconcile）

跨存储流程没有事务性：SQLite 事务管不住 ClickHouse 的 DDL。进程在“物理表已建但元数据未置 `active`”
之间崩溃，表会永远卡在 `creating` 且无人察觉。因此后端**每次启动时必须执行一次 reconcile**：

1. 读取 SQLite `collect_tables` 中所有 `creating` 和 `failed` 的表。
2. 对照 `system.tables` 判断物理表是否存在：存在则补写 `active` 元数据；不存在则置为 `failed`。
   同时对所有 `archived` 的表做一次物理表存在性检查：物理表不存在，说明 7.5 的删除只完成了 ClickHouse 侧，
   **只写一条告警日志，不做任何自动处理**，也不计入 `fixed` / `failed`——由操作者重新点一次删除收尾。
3. 对所有 `active` 和 `disabled` 的表，对照 `system.columns` 与 `collect_fields` 中 `status = 'active'` 的行做 schema drift 校验
   （`disabled` 也要查，因为字段变更接口对 `disabled` 表是放行的，它同样会产生跨存储的中间态；
   `creating` / `failed` 由第 2 步处理，`archived` 不再接受字段变更，两者都不需要 drift 校验）：
   - **先识别被打断的重命名**：同一张表里恰好有一个 `active` 却缺物理列的 Key、
     又恰好有一个没有任何元数据行的孤儿列、且两者物理类型一致时，判定为 7.3 第 2 步之后中断，
     执行反向 `RENAME COLUMN` 把孤儿列改回该 Key，数据随之回到原位，本轮该表不再做其它修复。
     条件任一不满足就退回下面的逐条修复。**这一条必须排在补列之前**——否则会给该 Key 补出一个空列，
     而历史数据永远留在孤儿列里，与本节「重命名不丢数据」的承诺相悖；
   - 元数据有、物理列没有 → 补 `ADD COLUMN`；
   - 物理列有、元数据完全没有记录行 → 记录告警日志，不自动处理；
   - 物理列有、元数据标记为 `dropped` → 说明上次删除只完成了元数据侧，补执行 `DROP COLUMN`；
   - **物理列在、但物理类型与元数据 `type` 按 6.6 映射出的不一致** → 分两种：
     `String` ⇄ `LowCardinality(String)` 这一对是 7.3 那条转换被打断的中间态，
     补一条 `MODIFY COLUMN` 收敛到元数据声明的类型；**其余任何不一致一律只记告警日志、不自动修复**——
     那意味着有人绕过接口直接改了 ClickHouse，自动 `MODIFY` 过去很可能让整列数据转换失败或被静默改写，
     这个决定必须由人来做。
4. reconcile 全程写结构化日志，失败不阻塞进程启动，但必须在 `/healthz` 中暴露最近一次 reconcile 的结果。

### 7.5 删除数据采集表

删除是 7.1 的镜像操作，**会永久销毁该表的全部历史数据**，是系统中爆炸半径最大的单个操作。

**前置条件**：只有 `archived` 和 `failed` 的表可以删除。

- `active` / `disabled` → 返回 `TABLE_STATE_CONFLICT`，必须先归档。归档是可逆的，
  这一步强制操作者先停掉上报入口，并留出一个反悔窗口。
- `creating` → 返回 `TABLE_STATE_CONFLICT`，等 7.4 的 reconcile 把它收敛到 `active` 或 `failed` 再说。
- `failed` 允许直接删除：这类表从未成功服务过，没必要走一遍归档的形式。

**二次确认**：请求体必须携带 `confirm`，值等于该表的 `displayName`，**不是 `projectId`**。
`projectId` 是随机 ULID，操作者对它没有任何认知，粘贴一下就过去了，起不到确认作用；
`displayName` 是操作者自己起的名字，能准确输入才说明知道自己在删什么。不一致返回 `CONFIRMATION_REQUIRED`。

**权限**：仅 `super_admin`。物理删除字段的爆炸半径是一列，删表是整个采集项目的全部历史，
比权限矩阵里任何一个 `admin` 操作都大一个数量级，因此单独收到最高一级。

执行顺序（跨存储操作，在 `serial()` 内）：

1. 读出该行，校验状态与 `confirm`。
2. `DROP TABLE IF EXISTS data.<physical_name> SYNC`（`ch_meta` 账户）。
3. 在一个 SQLite 事务内 `DELETE FROM collect_fields WHERE project_id = ?`，
   再 `DELETE FROM collect_tables WHERE project_id = ?`。

**顺序不能反过来。** 先删 SQLite 元数据再崩溃，物理表就成了孤儿：`physical_name` 是随机串，
指向它的元数据已经没了，reconcile 从 SQLite 出发永远发现不了它，只能靠人工比对 `system.tables` 才找得回来。
反过来先 `DROP TABLE` 再崩溃，留下的是「元数据有、物理表无」的中间态，这个中间态**无害且自愈**：
`archived` 表本就不接受上报、不接受字段变更、也不做 drift 校验，而操作者在列表里仍然看得见它，
**再点一次删除就能收尾**（`DROP TABLE IF EXISTS` 幂等，SQLite 侧照常执行）。
7.4 的 reconcile 会为这种表写一条告警日志，让它不至于无声无息。

**字段墓碑一并清除**：`collect_fields` 中该 `project_id` 的所有行——包括 `deprecated` / `dropped` /
`renamed` 墓碑——全部删除。墓碑的作用是防止**同一张表内**的 Key 被复用（见 5.2），表都不存在了，
墓碑也就失去了意义。重建的表有新的 `project_id`，Key 空间完全独立。

**为什么不引入 `deleting` 状态**：DROP 与 SQLite 删除之间的窗口是毫秒级、无害、且一键可修。
为它在状态机里加第六个终态，代价是 6.3 的 `CHECK` 约束变更（SQLite 无法 `ALTER` 掉 CHECK，
等于要求所有已部署的库做迁移）、状态机多一条分支、每个读接口都要处理一个新状态——不划算。

**不新增错误码**：状态不对用 `TABLE_STATE_CONFLICT`（409），`confirm` 不对用 `CONFIRMATION_REQUIRED`（400），
表不存在用 `TABLE_NOT_FOUND`（404），权限不足用 `FORBIDDEN`（403），全部复用已有的。
