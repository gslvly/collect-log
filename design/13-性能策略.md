## 13. 性能策略

V1 数据量不大，优先保证结构简单和行为正确。

- 业务字段使用明确物理列，避免 JSON 查询时的类型推断开销。
- 按月分区，便于时间范围查询和未来的数据保留策略。
- 排序键 `(toDate(_occurred_at), _occurred_at, _record_id)` 服务于时间范围查询与去重收敛。
- 使用 ClickHouse 服务端 async insert 合并小请求，并按 8.4 调优 part 落盘频率。
- 每次 INSERT 使用完整列集合，保证 async insert 攒批不被打散。
- Node 使用进程内 Map 缓存表元数据，不引入 Redis；字段变更后立即失效对应缓存。缓存值是「表属性 + active 字段白名单 + 各 `enum` 字段的 active 选项集合」的合并结果，上报路径命中缓存时不产生任何数据库查询。**缓存必须有容量上限，且不缓存「查不到」的空结果**：`projectId` 来自不可信输入，
  无上限的 Map 会被伪造 ID 撑爆内存。
  枚举值域一并进这份缓存，是因为 8.2.1 的第 11 步在上报热路径上——每条上报多打一次 SQLite 是不可接受的。
  选项变更（7.3）必须与字段变更走同一条失效路径。
- 不为每个字符串字段创建额外索引；确有热点过滤字段时再评估数据跳数索引。
- **`enum` 落到 `LowCardinality(Nullable(String))`，`string` 保持 `Nullable(String)`。**
  字典编码的收益（存储压缩、`GROUP BY` 与等值过滤提速）恰好落在最该受益的地方——
  分组统计几乎全部发生在枚举字段上；而它的代价（高基数时字典膨胀）被 `maxEnumOptions` 挡住了。
  这是「用类型表达基数」而不是「事后猜基数」：建表人选 `enum` 就等于声明了这一列是低基数的。
