## 10. 管理后台

### 10.1 页面

1. 登录页（用户名 + 密码 + 图形验证码）
2. 数据概览
3. 数据采集表列表
4. 创建数据采集表（弹窗表单，支持从现有表复制字段，见 10.5）
5. 字段配置与 Schema 版本
6. 上报接入文档（含密钥与可复制的 TypeScript 示例）
7. 数据明细查询
8. 统计分析
9. 账户管理

### 10.2 数据概览

- 今日总上报量（按用户时区）
- 最近 24 小时趋势
- 各数据采集表上报量
- 最近上报时间

不做“上传失败数量”卡片。上报失败不落库，只写结构化日志（见 12.4），排查时按 `requestId` 或 `projectId` 检索日志即可。

### 10.3 数据采集表详情

- 基本信息、公开 `projectId`
- 表状态与状态迁移操作
- 当前 Schema 版本
- 字段列表。**含全部状态的行**（`active` / `deprecated` / `dropped` / `renamed`），
  数据来自 15.3 的表详情接口。墓碑默认可以折叠，但不能查不到——
  操作者需要知道某个 Key 为什么建不了、以及它当初改成了什么名字
- 字段操作：新增、改名、编辑枚举选项、`string` ⇄ `enum` 转换、软废弃、物理删除。
  改名 / 软废弃 / 改 label 与必填 / 选项 / 转换只对 `active` 字段提供入口；
  **物理删除对 `active` 与 `deprecated` 都提供**（见 7.3），
  这是把一个软废弃字段彻底清掉、或腾出它的 Key 用于重建的唯一途径
- **字段类型只在 `string` ⇄ `enum` 之间可改**：这两种类型的字段上给一个「转换为枚举 / 转换为文本」
  入口（走 `retype`，数据完整保留）；其余类型旁固定展示一句提示
  「不能修改字段类型，请先删除该列，再新建同名列」，不提供一键改类型的入口，
  操作者按提示自行走「物理删除」+「新增字段」两个独立操作（见 7.3）
- **`string → enum` 的转换弹窗必须先展示历史值**：用统计接口拉一次该字段的 Top 取值
  （`dimension.kind = "field"`、`measure.fn = "count"`，见 9.4），
  每个值旁给一个「登记为选项」的勾选，默认全选。理由见 7.3：转换只约束今后的上报，
  历史值不会消失，但**没登记的值今后会被拒收**——不把它们摆在眼前，
  操作者就会在转换之后才发现线上开始报 `INVALID_FIELD_VALUE`
- **字段配置表单按类型联动**：选 `enum` 时展开选项编辑器（`value` / `label` / 启用开关，可拖拽排序，
  数量受 `maxEnumOptions` 约束）；其余类型不显示该区块。类型下拉每一项旁边给一句话说明用途，
  并对两处最容易选错的地方给出明确提示：
  - `integer` 旁：「大整数 ID（雪花 ID、订单号）请用文本类型，超过 2^53 的整数在浏览器里就已经不准了」（见 6.6）
  - `float` 旁：「小数不支持等值筛选，只能按范围过滤」（见 5.4.2）
- **选项编辑器不提供「删除」**，只有停用 / 启用（见 5.5）。已经在使用的选项被停用时，
  提示「历史数据仍可查询与分组，但新上报会被拒绝」。提交时按 15.4 的规则**带上全部现存选项**，
  前端不得只提交变更部分
- 删除本表（高危，仅 `super_admin` 可见，且仅在表为 `archived` / `failed` 时可用，见 7.5）
- 上报密钥查看与轮换
- 最近上报记录
- 接入示例代码（可一键复制）
- 统计分析入口

### 10.4 高危操作的交互要求

以下操作会造成**历史数据永久丢失**，必须在 UI 上做强提示与两级确认：

- 物理删除字段
- **删除数据采集表**（见 7.5，爆炸半径最大）

交互规范：

1. 按钮使用危险色（Element Plus `type="danger"`），且不能是列表行内的默认操作，必须收进「更多」菜单。
2. 第一级确认：弹窗标题明确写「此操作将永久删除该字段的全部历史数据」，正文列出字段 `key`、`label`、类型，以及该字段当前的非空行数（实时查询 `GET .../fields/:fieldKey/usage`，见 15.4），让操作者看到具体会丢多少数据。
   **行数取不到时禁用确认按钮**，只允许重试或取消——第 2、3 两条的全部意义就在于让操作者看着数字做决定，
   拿不到数字就等于盲删。（删表弹窗的总行数取不到时**不阻塞**删除，两边口径不同是有意的：
   删表的前置条件已经把表锁在 `archived` / `failed`，操作者早就停过一次上报、做过一次决定，
   而字段删除可以直接对一张服务中的 `active` 表发起。）
3. 第二级确认：要求用户**手动输入字段 Key** 完全一致才能激活确认按钮，不允许复制粘贴之外的快捷通过。
4. 提交时请求体必须携带 `confirm` 字段，值等于字段 Key，服务端二次校验，不一致返回 `CONFIRMATION_REQUIRED`。
5. 操作完成后的成功提示中，说明该列的历史数据已永久删除、不可恢复。**不要提示「Key 永久不可重新创建」**——
   按 5.2，`dropped` 的 Key 是可以重新创建的，只是建出的会是一列全新的空列。
6. 新建字段时若 Key 撞上 `deprecated` 的行（服务端返回 `FIELD_KEY_RETIRED`），提示必须指出出路：
   **「该 Key 已被软废弃字段占用，需先物理删除该列才能复用」**，而不是笼统的「不可用，请换一个」。
   撞上 `active` 行（`FIELD_KEY_EXISTS`）才是真的要换 Key。

跨类型族的换类型走的就是这条物理删除路径（见 7.3），前端不为它单开入口、也不做自动串联，
因此不需要额外的确认交互。`string` ⇄ `enum` 转换**不属于高危操作**——它不丢任何数据，
只需一级确认，弹窗里说明「历史数据完整保留；未登记的历史值今后将被拒收」即可。

字段重命名不丢数据，只需一级确认，但必须提示「前端上报代码需同步改用新字段名，否则该字段的上报会被拒绝」。

**删除数据采集表的额外要求**（在上述四条之上）：

1. 入口只在表详情页，不出现在列表页的行内操作里，且只对 `super_admin` 渲染。
   表状态不是 `archived` / `failed` 时按钮置灰，鼠标悬停说明「请先归档」。
2. 第一级确认弹窗必须实时查询并展示：表的 `displayName`、`projectId`、字段数、
   **该表当前的总行数**（`GET .../row-count`，见 15.3）、创建时间与创建人。让操作者看到具体会丢多少数据。
3. 第二级确认要求手动输入**表的 `displayName`** 完全一致才激活确认按钮。
4. 弹窗必须明确写出三条后果：历史数据永久销毁且无法恢复；该 `projectId` 立即失效，
   仍在使用它的前端埋点会开始收到错误；该表的字段 Key 墓碑一并清除。
5. 成功后跳回列表页，提示「已永久删除，无法恢复」。


### 10.5 从现有表复制字段（创建表单模板）

新建数据采集表的弹窗表单里，字段是一行一行填的，字段多的时候很枯燥，而实际场景中新表往往
和已有表高度相似（同一套埋点换个业务线、建失败了想改个名重来）。因此创建表单提供一个可选的
「从现有表复制字段」下拉，选中后把该表的字段定义回填进表单，**回填后完全可编辑**。

两个只读接口支撑这个交互：

```text
GET    /api/admin/tables/templates              # 下拉列表
GET    /api/admin/tables/:projectId/template    # 选中后取回填内容
```

**接口 1 — 下拉列表**。返回全部表的轻量信息，按 `created_at DESC` 排序（最近建的最可能被复制）：

```json
{
  "templates": [
    { "projectId": "prj_01K...", "displayName": "订单事件", "status": "active", "fieldCount": 7 }
  ]
}
```

表数量受附录 A 的 `maxTables` 约束，本就不会多，不分页。**所有状态的表都可以当模板**，
包括 `archived` 和 `failed`——「建失败了想重建」正是这个功能最常见的用途；`status` 一并返回，
供前端在下拉项上标注，让操作者知道自己在复制什么。

**接口 2 — 回填内容**。只返回表单需要的东西，**不含任何 ID、密钥、状态或版本号**：

```json
{
  "sourceDisplayName": "订单事件",
  "description": "下单链路埋点",
  "fields": [
    { "key": "event_name", "label": "事件名", "type": "string", "required": true, "description": "" }
  ]
}
```

- `sourceDisplayName` 只用于前端提示「已从《订单事件》复制 7 个字段」，**不回填到表名输入框**——
  否则很容易建出两张同名表。表名必须由操作者重新填写。
- `fields` 只包含源表 `collect_fields` 中 `status = 'active'` 的行，且剥掉 `schemaVersion`。
  `deprecated` / `dropped` / `renamed` 是墓碑和废弃记录，属于源表自己的历史，复制过去只是噪音；
  而且新表 `project_id` 不同，Key 空间独立，源表退役的 Key 在新表里**完全可以正常使用**。
- 表不存在返回 `TABLE_NOT_FOUND`。**不新增错误码。**
- 权限与建表一致（`admin`、`super_admin`）：只有能建表的人才需要模板。

**服务端不知道模板的存在**。回填只是把表单的初始值换了一批，用户改完之后照常提交
`POST /api/admin/tables`，请求体和手工填写完全一样，**不引入 `templateFrom` 之类的参数**。
否则 `templateFrom` 和 `fields` 会构成两个真值来源，「两个都传时谁赢」这条规则迟早有人搞错。

**回填内容不享受任何豁免**。提交时照样要过建表的全部校验：Key 格式与保留字、类型合法性、
重复 Key、`maxFields` 限额。源表当初能通过不代表新表能通过——限额可能被调小过，
所以前端不能假设回填进来的内容一定合法。

**覆盖提示**：表单里已经有编辑过的字段时再次选择模板，必须先确认是否覆盖，避免一次误操作抹掉手工填的内容。


### 10.6 查询构建器与统计页

这两个页面共用同一条硬性约束：**可选项一律来自服务端，前端不硬编码任何「类型 → 能力」的知识。**
启动时拉一次 `GET /api/admin/field-types`（见 15.8）缓存起来，
再结合表详情里每个字段的 `type`，就能渲染出全部下拉。

查询构建器（明细页的筛选区）：

- 选中字段后，操作符下拉只列该字段 `type` 对应的 `operators`。**不要把不可用的操作符置灰后仍然显示**
  ——操作者会花时间琢磨「为什么这个不能选」，而答案（浮点不能等值）需要一整段解释才说得清。
- 值输入控件按 `type` 切换：`enum` 用选项下拉（单选 / 多选取决于操作符的 `arity`，
  选项含已停用项但需灰显并标注「已停用」）；`boolean` 用是 / 否单选；
  `integer` / `float` 用数字输入；`datetime` 用日期时间选择器，提交时转成 Unix 毫秒；
  `string` 用文本输入。`arity: "none"` 的操作符（`is_null` 等）不显示值输入。
- 已废弃字段可以出现在筛选区，但要标注「已废弃」（服务端对 `filter` 直接放行，见 9.1）。

统计页：

- 两个下拉对应 9.4 的两个轴：**「按什么分组」**（不分组 / 时间 / 某个字段）和
  **「统计什么」**（指标 + 字段）。
- 维度下拉只列具备 `groupable` 的字段，外加「时间」一项；选「时间」后再选时间轴
  （`_occurred_at` 或任意 `datetime` 字段）与粒度。
- 指标下拉先选 `fn`，再选字段，字段列表按该 `fn` 需要的能力过滤
  （例如选了 `sum` 就只列 `integer` / `float` 字段）。
- **`string` 字段在维度下拉里标注「高基数字段分组可能较慢」**（见 5.4.3）。系统不阻止，
  但要让操作者在点下去之前知道自己在做什么；真的超限时服务端会返回 `INVALID_QUERY`（见 9.1）。
- 结果区必须展示三样东西，缺一不可（对应 9.4.4 的响应字段）：`totals` 的总量、
  `truncated` 为真时的「仅显示前 N 项」提示、以及 `others`（有则画成图例最后一档）。
- **`avg` / 分位数的口径必须写在图表旁**：「分母是该字段非空的行数」（见 9.4.2）。
  少了这句，「平均耗时」会被当成「所有请求的平均耗时」而系统性偏高，
  这是一个不会报错、只会让人做出错误判断的坑。
