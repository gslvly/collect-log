## 8. 上传接口

### 8.1 上报防护：HMAC-SHA256 签名

**安全边界声明（必读）**：密钥保存在前端就是公开的，混淆只能提高逆向门槛，无法真正保密。这套机制的定位是 **anti-casual-abuse（阻止随手刷接口）**，**不是身份认证**。因此：

- 上报接口的全部输入都是**不可信数据**。
- 上报数据中的任何字段（包括自定义的 `user_id` 之类）**不构成身份证明，禁止用于任何权限判断**。
- 密钥泄露的后果是数据被污染，不涉及越权读取——上报账户只有 `data.*` 的 INSERT 权限。

#### 8.1.1 Envelope 格式

签名信息**放在 body 内而不是 HTTP 头**。这是刻意的：任何 `X-` 自定义请求头都会触发 CORS 预检，而预检在页面卸载期间基本发不出去，`sendBeacon` 会直接失效。把签名放进 body 并使用 `text/plain;charset=UTF-8`，请求就是 CORS 简单请求，无预检，`sendBeacon` 和 `fetch keepalive` 都能正常工作。

```http
POST /api/ingest/v1/projects/:projectId/rows
Content-Type: text/plain;charset=UTF-8
```

```json
{
  "p": "prj_01KABCDEF...",
  "t": 1756012830123,
  "n": "a3f9c2d1b7e40851",
  "s": "9b1f4c...64位hex...",
  "d": "{\"recordId\":\"bea94960-7fbe-4853-a689-8a309c471627\",\"occurredAt\":1756012830123,\"data\":{\"login_method\":\"sms\",\"result\":\"success\",\"remember_me\":true}}"
}
```

| 字段 | 含义 |
|---|---|
| `p` | `projectId` |
| `t` | 客户端毫秒时间戳，用于时间窗校验 |
| `n` | 随机 nonce，16 位 hex |
| `s` | 签名，hex 小写 |
| `d` | **原始明文 JSON 字符串**，即真正的上报载荷 |

`d` 保持字符串而非嵌套对象，是为了让签名针对确切的字节序列，服务端直接对收到的 `d` 验签后再 `JSON.parse`，彻底避免 JSON key 顺序导致的签名不一致。

#### 8.1.2 签名算法

```text
signBase  = p + "\n" + t + "\n" + n + "\n" + d
signature = hex(HMAC_SHA256(ingestSecret, signBase))
```

服务端校验顺序：

1. `p` 与 URL 中的 `projectId` 一致，且能查到对应的采集表。
   （签名覆盖的是 `p` 而不是 URL，因此这一步是纵深防御：即使跳过，拿 A 项目的信封打 B 项目的
   URL 也会在第 4 步用 B 的密钥验签失败，但显式比对能给出更准确的错误。）
2. `|now - t| <= 5min`，否则 `SIGNATURE_EXPIRED`。
3. `n` 在进程内 LRU（容量 10 万，TTL 5 分钟）中未出现过，否则 `REPLAYED_NONCE`。重启后该窗口清空，最多允许 5 分钟内的重放——由于重放行的 `recordId` 相同，`ReplacingMergeTree` 会收敛，影响可以忽略。
4. 用 `ingest_secret` 计算签名，用 `crypto.timingSafeEqual` 比较；不匹配时再用 `ingest_secret_prev` 试一次（支持轮换灰度期）。

密钥轮换：后台生成新密钥时，旧密钥自动移入 `ingest_secret_prev`，
`ingest_secret_prev_expires_at` 置为 7 天后。校验第 4 步回退到旧密钥前必须先检查该时刻是否已过；
已过期则视同没有旧密钥。前端灰度完成后也可手动提前清除。

#### 8.1.3 前端上报示例（TypeScript）

创建采集表后，后台直接展示以下可复制代码。前端可对 `INGEST_SECRET` 自由做常量拆分、字符串混淆或构建期注入。

```ts
// log-client.ts
export interface LogClientConfig {
  endpoint: string;   // https://log.example.com
  projectId: string;  // prj_01KABCDEF...
  secret: string;     // ingestSecret，可自行混淆
}

/**
 * string / enum → string；boolean → boolean；
 * integer / float / datetime → number（datetime 传 Unix 毫秒时间戳，见 5.4.1）。
 * 六种字段类型在传输层上只有这三种 JSON 值，区分由服务端按 Schema 完成（见 8.2.1）。
 */
export type LogValue = string | boolean | number;

const encoder = new TextEncoder();
let cachedKey: Promise<CryptoKey> | null = null;

function importKey(secret: string): Promise<CryptoKey> {
  cachedKey ??= crypto.subtle.importKey(
    'raw',
    encoder.encode(secret),
    { name: 'HMAC', hash: 'SHA-256' },
    false,
    ['sign'],
  );
  return cachedKey;
}

function toHex(buffer: ArrayBuffer): string {
  return Array.from(new Uint8Array(buffer))
    .map((b) => b.toString(16).padStart(2, '0'))
    .join('');
}

async function buildEnvelope(
  config: LogClientConfig,
  data: Record<string, LogValue>,
): Promise<string> {
  const payload = JSON.stringify({
    recordId: crypto.randomUUID(),
    occurredAt: Date.now(),
    data,
  });

  const timestamp = Date.now();
  const nonce = toHex(crypto.getRandomValues(new Uint8Array(8)).buffer);
  const signBase = `${config.projectId}\n${timestamp}\n${nonce}\n${payload}`;
  const signature = toHex(
    await crypto.subtle.sign('HMAC', await importKey(config.secret), encoder.encode(signBase)),
  );

  return JSON.stringify({ p: config.projectId, t: timestamp, n: nonce, s: signature, d: payload });
}

/** 常规上报。失败只记录，不抛出，避免影响业务流程。 */
export async function report(
  config: LogClientConfig,
  data: Record<string, LogValue>,
): Promise<boolean> {
  try {
    const body = await buildEnvelope(config, data);
    const res = await fetch(`${config.endpoint}/api/ingest/v1/projects/${config.projectId}/rows`, {
      method: 'POST',
      headers: { 'Content-Type': 'text/plain;charset=UTF-8' },
      body,
      keepalive: true,
    });
    return res.ok;
  } catch {
    return false;
  }
}

/** 页面卸载场景。sendBeacon 无法重试，属于尽力而为。 */
export async function reportOnUnload(
  config: LogClientConfig,
  data: Record<string, LogValue>,
): Promise<boolean> {
  const body = await buildEnvelope(config, data);
  const blob = new Blob([body], { type: 'text/plain;charset=UTF-8' });
  return navigator.sendBeacon(`${config.endpoint}/api/ingest/v1/projects/${config.projectId}/rows`, blob);
}
```

使用：

```ts
const client: LogClientConfig = {
  endpoint: 'https://log.example.com',
  projectId: 'prj_01KABCDEF...',
  secret: import.meta.env.VITE_LOG_SECRET,
};

// 下面每个 Key 都是建表时自己配的字段，系统对它们的业务含义一无所知；
// 值也全部由业务代码自己算好传上来，没有任何一项是被自动采集的。
await report(client, {
  user_id: '10086',             // string
  login_method: 'sms',          // enum，必须是后台登记过的选项
  result: 'success',            // enum
  remember_me: true,            // boolean
  retry_count: 2,               // integer
  cost_seconds: 1.37,           // float
  registered_at: 1743148800000, // datetime，Unix 毫秒
});
```

注意 `Content-Type` 必须保持 `text/plain;charset=UTF-8`，改成 `application/json` 会触发 CORS 预检并使 `sendBeacon` 失效。

### 8.2 校验流程

1. 解析 envelope，校验 `p` / `t` / `n` / `s` / `d` 均存在且为期望类型。
2. 按 8.1.2 完成签名校验。
3. 校验 `projectId` 格式，从内存缓存读取当前表定义；缓存未命中时查 SQLite：`collect_tables` 取表级属性，`collect_fields WHERE status = 'active'` 取字段白名单。
4. 确认表状态为 `active`（`disabled` / `archived` 返回 `TABLE_DISABLED`，`creating` 返回 `TABLE_NOT_READY`）。
5. 校验 envelope 与 `d` 的大小、字段数量。
6. `JSON.parse(d)`，校验 `recordId` 为合法 UUID（缺省时由服务端生成）。
7. **校验 `occurredAt`**：必须是数字毫秒时间戳，且落在 `[now - 7d, now + 5min]`，否则返回 `INVALID_OCCURRED_AT`。该校验是 6.5 分区安全性的前提，不可省略。
8. 拒绝未知字段和已废弃的字段。
9. 校验必填字段。
10. **按字段 `type` 校验 JSON 值的类型**，不符返回 `INVALID_FIELD_TYPE`（见 8.2.1）。
11. **按字段 `type` 校验值域**，不符返回 `INVALID_FIELD_VALUE`（见 8.2.1）。
12. 使用字段白名单构造 INSERT 列表。
13. 写入系统字段、Schema 版本和业务字段。

物理表名和列名不能使用普通 SQL 参数绑定，因此必须来自服务端白名单；所有字段值必须参数化。

#### 8.2.1 按类型的值校验

第 10 步管**类型**（这个 JSON 值是不是该字段能接受的形状），第 11 步管**值域**
（形状对了，但这个具体的值允许不允许）。两步分开是为了让错误码能区分开：
`INVALID_FIELD_TYPE` 是「你该传数字却传了字符串」，`INVALID_FIELD_VALUE` 是
「你传的数字不是整数」或「你传的枚举值没登记过」——这两种错误的修法完全不同，
混成一个码会让调用方在错误的方向上排查。

| `type` | 第 10 步：JSON 类型 | 第 11 步：值域 | 值域不符时 |
|---|---|---|---|
| `string` | `typeof === 'string'` | UTF-8 字节数 ≤ `maxStringLength` | `FIELD_VALUE_TOO_LONG` |
| `enum` | `typeof === 'string'` | 命中该字段 `status = 'active'` 的选项 `value` | `INVALID_FIELD_VALUE` |
| `boolean` | `typeof === 'boolean'` | — | — |
| `integer` | `typeof === 'number'` | `Number.isInteger(v)` 且 `Math.abs(v) <= 2^53 - 1` | `INVALID_FIELD_VALUE` |
| `float` | `typeof === 'number'` | `Number.isFinite(v)`（拒绝 `NaN` / `±Infinity`） | `INVALID_FIELD_VALUE` |
| `datetime` | `typeof === 'number'` | 整数毫秒，且落在 `[datetimeMinMs, datetimeMaxMs]` | `INVALID_FIELD_VALUE` |

四点说明：

- **`NaN` / `Infinity` 在 JSON 里根本不存在**（`JSON.stringify(NaN)` 得到 `null`），
  所以第 11 步对 `float` 的这条校验实际拦的是手写载荷的调用方。它必须有：
  这类值写进 ClickHouse 之后，该列上的 `avg` / `sum` 会全部变成 `nan`，一列数据当场报废。
- **`datetime` 的窗口比 `occurredAt` 宽得多**，两者不是一回事：`occurredAt` 决定分区，
  必须卡在 `[now-7d, now+5min]`（见 6.5）；业务时间字段不进分区键、不进排序键，
  写一个三年前的注册时间完全合理，只要挡住明显非法的值即可（见附录 A）。
- **`enum` 的值域校验读的是缓存**。`active` 选项集合与字段白名单同属一份进程内缓存值（见 13），
  选项变更后立即失效，因此不会为每条上报多打一次 SQLite。
- **`required` 只管「有没有」，不管「是不是空」**：`required` 的 `string` 字段提交 `""` 视为已提交
  （空串与 `NULL` 是两回事，见 6.6）。要求非空是业务约束，不是采集系统的职责。

### 8.3 响应

成功（HTTP 200）：

```json
{
  "success": true,
  "recordId": "bea94960-7fbe-4853-a689-8a309c471627",
  "requestId": "req_01K..."
}
```

失败（HTTP 4xx / 5xx），全站统一错误响应体：

```json
{
  "success": false,
  "error": {
    "code": "INVALID_FIELD_VALUE",
    "message": "field \"login_method\" expects one of the registered options, got \"wechat_mini\"",
    "field": "login_method",
    "expected": {
      "key": "login_method",
      "label": "登录方式",
      "type": "enum",
      "required": true,
      "options": ["sms", "password"]
    },
    "schemaVersion": 7
  },
  "requestId": "req_01K..."
}
```

**字段类错误必须回传该字段在当前 Schema 中的定义**（`error.expected` 直接取自 `collect_fields` 中该字段的 `active` 行）。因为校验依据完全来自建表时配置的字段，把这份定义连同错误一起返回，前端不用翻后台文档就能立刻知道该传什么；这也是不建失败统计表的前提——错误本身已经自解释。适用于 `UNKNOWN_FIELD`、`DEPRECATED_FIELD`、`REQUIRED_FIELD_MISSING`、`INVALID_FIELD_TYPE`、`INVALID_FIELD_VALUE`、`FIELD_VALUE_TOO_LONG`。

**`expected.options` 仅 `enum` 字段有**，内容是当前 `status = 'active'` 的选项 `value` 列表
（受 `maxEnumOptions` 截断，截断时在 `message` 里说明还有多少个）。
它是「自解释」这条原则在枚举上的落点：值域是后台配的，调用方无从得知，
不把允许的值列出来，`INVALID_FIELD_VALUE` 就只是一句「你错了」。已停用的选项**不出现在这个列表里**
——它们正是被拒的原因之一，列出来会让人以为还能用。

`UNKNOWN_FIELD` 没有对应定义，此时 `expected` 省略，改为在 `message` 中列出当前允许的字段 Key 列表（受 `maxFields` 截断）。

`error.field` 仅在错误与某个具体字段相关时出现。`requestId` 由 Fastify 在请求入口生成（ULID），贯穿全部结构化日志，响应中原样返回，便于用户报障时定位。

错误码与 HTTP 状态映射：

| HTTP | 错误码 |
|---:|---|
| 400 | `INVALID_JSON`、`INVALID_ENVELOPE`、`INVALID_PROJECT_ID`、`INVALID_RECORD_ID`、`INVALID_OCCURRED_AT`、`INVALID_FIELD_KEY`、`UNKNOWN_FIELD`、`DEPRECATED_FIELD`、`REQUIRED_FIELD_MISSING`、`INVALID_FIELD_TYPE`、`INVALID_FIELD_VALUE`、`FIELD_VALUE_TOO_LONG`、`TOO_MANY_FIELDS`、`INVALID_QUERY`、`CONFIRMATION_REQUIRED` |
| 401 | `INVALID_SIGNATURE`、`SIGNATURE_EXPIRED`、`REPLAYED_NONCE`、`UNAUTHORIZED`、`TOKEN_EXPIRED`、`INVALID_CREDENTIALS`、`INVALID_CAPTCHA` |
| 403 | `FORBIDDEN`、`TABLE_DISABLED` |
| 404 | `TABLE_NOT_FOUND`、`FIELD_NOT_FOUND`、`USER_NOT_FOUND`、`ROUTE_NOT_FOUND` |
| 409 | `USERNAME_EXISTS`、`FIELD_KEY_EXISTS`、`FIELD_KEY_RETIRED`、`TABLE_STATE_CONFLICT`、`LAST_SUPER_ADMIN` |
| 413 | `PAYLOAD_TOO_LARGE` |
| 415 | `UNSUPPORTED_MEDIA_TYPE` |
| 429 | `RATE_LIMITED` |
| 500 | `INTERNAL_ERROR`、`INSERT_FAILED` |
| 503 | `TABLE_NOT_READY`、`CLICKHOUSE_UNAVAILABLE` |

表中最后两个错误码是为了守住「**全站统一错误响应体**」这句承诺而存在的，本身不代表新的业务语义：

- `ROUTE_NOT_FOUND`（404）：上表其余 404 都是资源级的（表 / 字段 / 用户不存在），
  而「路径根本没注册」走的是框架的兜底 404。用 `setNotFoundHandler` 把它接过来，
  未匹配路由同样返回上面那个响应体，而不是框架自带的另一种形状。
- `UNSUPPORTED_MEDIA_TYPE`（415）：Fastify 内建的 `FST_ERR_CTP_INVALID_MEDIA_TYPE` 就是 415。
  不给它一个错误码，它就会掉进兜底分支被降级成 500——把「你的 `Content-Type` 不对」
  说成「服务器内部错误」，会把调用方引向完全错误的排查方向。

`INVALID_FIELD_VALUE`（400）是 V4 随类型系统一起引入的唯一新错误码，覆盖**形状正确但取值不合法**
的全部场景，上报侧与管理侧共用：枚举值未登记、`integer` 收到小数、`float` 收到 `NaN`、
`datetime` 超窗（见 8.2.1）；以及管理侧的选项列表非法、`enum` 字段建表时没带选项、
非 `enum` 字段带了选项、对非 `enum` 字段调选项接口（见 5.5 / 7.3 / 15.4）。
它与 `INVALID_FIELD_TYPE` 的分界是「形状 vs 取值」，理由见 8.2.1。

**除本表之外不得新增或改名任何错误码。**

### 8.4 写入策略

不在 Node 内存中攒批，攒批交给 ClickHouse 服务端的 async insert 完成。

**原理**：请求到达 ClickHouse 后，数据先进入服务端内存 buffer，buffer 按 `(查询文本, settings, 用户, 表)` 分组；当 buffer 达到 `async_insert_max_data_size` 或距首次写入超过 `async_insert_busy_timeout_max_ms` 时，整个 buffer 合并成**一个 part** 落盘。`wait_for_async_insert=1` 让 HTTP 响应挂起到 part 真正落盘才返回。

由此得出两条硬性要求：

- **每次 INSERT 必须使用该表的完整列集合**，未提交的字段显式写 `NULL`。因为 buffer 是按查询文本分组的，按实际提交字段动态拼列名会把攒批打散成几十个队列，part 数暴涨。
- **参数值必须走数据通道**（CH Node Client 的 `insert()` 传 `JSONEachRow` 行数组），不能拼进查询文本，否则每行都是不同的查询文本，攒批彻底失效。

上报路径的 query-level settings：

```ts
await client.insert({
  table: `data.${physicalName}`,
  values: [row],
  format: 'JSONEachRow',
  clickhouse_settings: {
    async_insert: 1,
    wait_for_async_insert: 1,
    async_insert_busy_timeout_max_ms: 1000,
    async_insert_max_data_size: '1048576',
  },
});
```

`async_insert_busy_timeout_max_ms` 取 1000ms 是刻意的取舍：默认约 200ms 会产生约 5 parts/s 的落盘频率，后台 merge 压力大；放宽到 1s 让 part 数下降约 5 倍，代价是 ingest 请求 p99 延迟约 1s。由于上报是异步旁路调用，这个延迟对业务无感。

其他：

- `_occurred_at` 由前端以毫秒数字传入，服务端转换为 `'YYYY-MM-DD HH:MM:SS.sss'`（UTC）写入。
- `_received_at` 由 ClickHouse `now64(3)` 生成，客户端不可控。
- V1 只支持单行上传；后续可以增加批量接口。
- 前端需要自行处理失败重试，重试必须复用同一个 `recordId`。
- 页面退出场景使用 `sendBeacon`（不可重试）或 `fetch keepalive`。

### 8.5 幂等边界

调用方必须为每一行生成稳定的 `recordId`，重试时保持不变。

`data.collect_*` 使用 `ReplacingMergeTree(_received_at)`，去重键包含 `_record_id`。同一 `recordId` 的重复写入会在后台 merge 时收敛为一行。但要理解两点限制：

1. **收敛不是实时的。** merge 由 ClickHouse 后台调度，查询不加 `FINAL`，因此短期内可以查到重复行。
2. **跨分区不收敛。** ReplacingMergeTree 只在分区内去重。由于分区键基于客户端固定的 `_occurred_at`，正常重试不会跨分区，但如果调用方在重试时修改了 `occurredAt`，去重就会失效。

结论：V1 提供**尽力去重，不承诺 Exactly Once**，精确计数不是本系统的目标（见 2.1）。**前端应自行做本地去重**，避免同一事件重复发送。

如果未来业务真的需要严格全局去重，需要引入专门的幂等存储或 `ReplicatedMergeTree` + Keeper（后者才有块级 `insert_deduplicate`，普通 `MergeTree` 完全没有这个能力）。
