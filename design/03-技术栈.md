### 3.3 存储

V1 使用两个存储，各司其职，**不引入 MySQL、PostgreSQL、Redis 和消息队列**：

| 存储 | 保存什么 | 为什么 |
|---|---|---|
| **SQLite** | 后台账户、数据采集表元数据、字段定义 | 低频小数据量，但需要**事务**和**唯一约束** |
| **ClickHouse** | 实际采集数据（`data.collect_*`） | 高频追加写入、列式压缩、时间范围聚合 |

要求 ClickHouse 部署**当前最新稳定版**（最低 24.8 LTS，需要 `Bool` 类型与轻量 `DELETE`）。
SQLite 使用 Node 内置的 `node:sqlite`，不引入原生编译依赖。

#### 3.3.1 为什么元数据不放在 ClickHouse

账户和元数据是典型的读-改-写小事务，而 ClickHouse 恰好不擅长这个：没有事务、没有唯一约束、
`UPDATE` / `DELETE` 是异步 mutation。把它们塞进 ClickHouse 需要一整套代偿机制——追加版本行、
`ReplacingMergeTree` 去重、每次读加 `FINAL`、由应用层查询校验唯一性、用串行队列避免版本覆盖。
这套机制不仅复杂，而且**静默失败的代价极高**：并发写回同一个 `version` 会被去重悄悄丢弃一条，
留下「ClickHouse 列已加但元数据没记」的不一致状态。

SQLite 用一行 `UNIQUE` 约束和一个 `BEGIN IMMEDIATE` 事务就解决了全部问题，因此 V3 改用 SQLite。
采集数据不动——那是纯追加、无更新、大数据量的负载，正是 ClickHouse 的主场。

#### 3.3.2 持久化目录

所有落盘数据收敛到**一个根目录**，由 `DATA_DIR` 配置，上线时只需挂载这一个卷：

```text
$DATA_DIR/
├── sqlite3/
│   └── app.db          # 账户 + 采集表元数据 + 字段定义（含 -wal / -shm）
└── clickhouse/         # ClickHouse 数据卷挂载点
```

Node 只直接读写 `$DATA_DIR/sqlite3/`；`$DATA_DIR/clickhouse/` 由 ClickHouse 服务进程自己使用，
Node 不碰，在这里列出是为了让部署时的卷挂载集中在一处。启动时若 `$DATA_DIR/sqlite3/` 不存在则自动创建。

必须启用的 PRAGMA：

```sql
PRAGMA journal_mode = WAL;     -- 读写不互相阻塞
PRAGMA foreign_keys = ON;      -- 字段行必须挂在存在的采集表上
PRAGMA busy_timeout = 5000;    -- 避免瞬时锁竞争直接报错
PRAGMA synchronous = NORMAL;   -- WAL 下的推荐值
```

V1 仍然只部署**一个 Node 后端实例**。跨存储的操作（SQLite 元数据 + ClickHouse DDL）
天然不具备原子性，仍然通过状态机与启动期 reconcile 恢复（见 7.4）。

#### 3.3.3 并发模型：上报不加锁，元数据走事务

- **上报路径不加任何锁。** 纯 append，没有读-改-写，加锁只会成为瓶颈。
- **纯 SQLite 的元数据读-改-写用事务。** 账户增删改、改 label / required、状态迁移、密钥轮换，
  一律包在 `BEGIN IMMEDIATE ... COMMIT` 内。唯一性由 `UNIQUE` 约束保证，冲突时由数据库报错，
  应用层把它翻译成 `USERNAME_EXISTS` / `FIELD_KEY_RETIRED`，**不再靠先查后写**——
  先查后写在并发下必然有窗口。
- **跨存储的操作仍然串行。** 建表、加字段、改名、删字段这几个操作要同时动 ClickHouse DDL 和
  SQLite 元数据，两者无法放进同一个事务。这些操作继续经过同一条 Promise 链串行执行，
  保证任一时刻只有一个跨存储流程在跑，把中间态收敛到「要么 reconcile 能修，要么根本没开始」。
  它们是人工触发的低频操作，串行化的性能代价为零。

```ts
// src/infra/serial.ts —— 跨存储（ClickHouse DDL + SQLite 元数据）操作的唯一入口
let chain: Promise<unknown> = Promise.resolve();

export function serial<T>(fn: () => Promise<T>): Promise<T> {
  const next = chain.then(fn, fn);
  chain = next.catch(() => {});
  return next;
}
```

如果未来需要多后端实例或高频管理操作，把 SQLite 换成 PostgreSQL 即可，业务代码基本不动。

### 3.4 ClickHouse 账户划分

必须使用三个独立账户，权限互不重叠：

| 账户 | 权限 | 用途 | `async_insert` |
|---|---|---|---|
| `ch_ingest` | `data.*` 的 `INSERT` | 上报写入 | 在**查询级**显式开启 |
| `ch_meta` | `data.*` 的 `CREATE/ALTER/DROP/SELECT`；`system.*` 的 `SELECT` | 建物理表、字段 DDL、reconcile 比对 | **必须关闭** |
| `ch_readonly` | `data.*` 的 `SELECT` | 后台查询、统计、导出 | 不适用 |

元数据已迁到 SQLite，ClickHouse 侧不再有 `meta` 库。但 `async_insert` 仍然**只能作为上报路径的
query-level setting 传入，绝不能配在账户或全局配置上**：一旦配在 user profile 上，
reconcile 里紧跟在 DDL 之后的 `system.columns` 比对就可能读到陈旧结果，让 schema drift 校验随机误判。
