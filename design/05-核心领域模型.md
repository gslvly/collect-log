## 5. 核心领域模型

### 5.1 数据采集表

数据采集表是系统的数据隔离单元，V1 中一张表对应一个产品项目。

主要属性：

- 公开 `projectId`：唯一公开标识，既是路由标识也是上报签名主体。**一个项目对应一张采集表**
- `ingestSecret`：HMAC 上报密钥（详见 8.1）
- 内部 ClickHouse 物理表名
- 显示名称、描述
- 状态
- 当前 Schema 版本
- 创建人用户名快照和创建时间

字段不是本实体的内嵌属性，而是独立实体，一个字段一行存放于 SQLite 的 `collect_fields`（见 6.4）。

状态与允许的迁移：

| 当前状态 | 含义 | 允许迁移到 |
|---|---|---|
| `creating` | 正在创建物理表 | `active`、`failed` |
| `active` | 允许上传和查询 | `disabled`、`archived` |
| `disabled` | 停止上传，仍允许查询 | `active`、`archived` |
| `archived` | 归档，只允许历史查询 | `active` |
| `failed` | 创建或变更失败 | `creating`（重试）、`archived` |

任何不在上表中的迁移请求返回 `TABLE_STATE_CONFLICT`。

数据采集表**可以被物理删除**，但只允许从 `archived` 或 `failed` 出发，需要二次确认与 `super_admin` 权限，见 7.5。删除不引入新的表状态——`active` / `disabled` 必须先归档，归档本身是可逆的，这一步就是防误删的冷静期。

### 5.2 字段

V1 字段定义只包含必要信息：

```json
{
  "key": "login_method",
  "label": "登录方式",
  "type": "enum",
  "required": true,
  "deprecated": false,
  "description": "本次登录使用的方式",
  "options": [
    { "value": "sms", "label": "短信验证码", "status": "active" },
    { "value": "password", "label": "密码", "status": "active" }
  ]
}
```

字段属性：

- `key`：对应 ClickHouse 物理列名，发布后不可修改
- `label`：管理后台展示名称，可以修改
- `type`：六种之一，见 5.4。**除 `string` ⇄ `enum` 之外发布后不可修改**（见 5.3 / 7.3）
- `required`：当前 Schema 版本上传时是否必填
- `deprecated`：是否已软废弃（列和历史数据仍在）
- `description`：字段说明
- `options`：**仅 `enum` 字段有**，是该字段的值域，见 5.5。其余五种类型该数组恒为空，
  提交非空数组返回 `INVALID_FIELD_VALUE`

字段上**没有「可用哪些操作符」「可做哪些统计」之类的开关**。这些能力由 `type` 唯一决定（见 5.4），
理由见 5.4 末尾那三段。字段级唯一可配的是 `enum` 的值域（`options`），
那回答的是「这个字段能取哪些值」，与「这个类型支持哪些操作」是两层，不要混。

字段 Key 规则：

- 必须匹配 `^[a-z][a-z0-9_]{0,63}$`（该正则已经排除了 `_` 前缀，系统字段因此天然不会被占用）。
  不匹配时返回 `INVALID_FIELD_KEY`（400，见 8.3）——建表、新增字段、重命名的目标 Key、
  以及路径参数 `:fieldKey` 全部走同一条校验，错误码一致
- 只要求在同一数据采集表内唯一
- 同一时刻只能有一行 `active`：`(project_id, field_key)` 是主键，Key 正被占用时重复创建直接被数据库拒绝，返回 `FIELD_KEY_EXISTS`
- **`deprecated` 的 Key 不能直接复用**，返回 `FIELD_KEY_RETIRED`：该状态下物理列与历史数据都还在，同名重建会让元数据里的类型与物理列脱节（`ADD COLUMN IF NOT EXISTS` 对已存在的物理列是空操作，元数据说新类型、物理列还是旧类型）。
  但这不是死路：**先对该字段执行物理删除**（7.3，`deprecated` 与 `active` 一样可删），Key 随之落到 `dropped` 墓碑上，再按下一条重建即可。软废弃因此是可退出的中间态，而不是终态
- **`dropped` / `renamed` 的 Key 可以重新创建**：这两种状态下该 Key 名下已经没有物理列了（`dropped` 的列在删除时就已 DROP，`renamed` 的数据跟着新 Key 走了），重建时先删掉那行墓碑再插入新的 `active` 行，建出的是一列全新的空列，**全程不触碰任何物理列与历史数据**。
  代价必须知情：被删除 / 改名之前的旧上报代码如果还在发这个 Key，原本会收到 `UNKNOWN_FIELD`，Key 一旦重建就会重新被接受并写进新列，与新数据混在一起（类型不同则报 `INVALID_FIELD_TYPE`）。因此重建同名 Key 前要确认调用方已经改完
- **跨类型族的「修改字段类型」**正是靠这条规则达成：系统对这类变更不提供接口，操作者按提示自行「物理删除 → 用同名 Key 新建」（见 7.3）。Key 在两步之间停在 `dropped` 墓碑上，新建时再把墓碑清掉、建出一列全新的空列（见 5.3）。
  唯一的例外是 `string` ⇄ `enum`：这两者物理同族、转换无损，有专门的接口且不丢数据（见 5.3 / 7.3）

### 5.3 Schema 版本

**判据只有一条：凡是会改变「同一份上报载荷在服务端的校验结果」的变更，版本加一；只影响后台展示的不加。**
新增字段、修改必填规则、增删枚举选项、废弃字段、删除字段、`string` ⇄ `enum` 转换都属于前者。

每行采集数据写入当时的版本号，便于解释历史数据。

字段变更规则：

| 操作 | 是否允许 | 数据影响 | 处理方式 |
|---|---:|---|---|
| 修改字段显示名称 | 是 | 无 | 只修改元数据，版本不变 |
| 修改字段描述 | 是 | 无 | 只修改元数据，版本不变 |
| 修改是否必填 | 是 | 无 | 只修改校验规则，版本加一 |
| 新增字段 | 是 | 无 | `ADD COLUMN`，版本加一 |
| **重命名字段 Key** | 是 | **数据完整保留** | `RENAME COLUMN`，旧 Key 行置 `renamed`，新增一行 `active`，版本加一 |
| 修改枚举选项的 `label` / 顺序 | 是 | 无 | 只修改元数据，版本不变（不影响上报校验） |
| **新增 / 停用 / 重新启用枚举选项** | 是 | 无 | 只修改校验规则与前端下拉，版本加一（见 5.5） |
| 删除枚举选项 | **不提供** | — | 历史数据里可能仍有该值，删掉选项等于丢掉它的 `label`。只能停用（见 5.5） |
| **`string` ⇄ `enum` 转换** | 是 | **数据完整保留** | `MODIFY COLUMN` 换编码，值不变，版本加一（见 7.3） |
| **其余任意两种类型之间的转换** | **不提供** | — | 没有接口也没有入口；操作者自行「物理删除」+「同名新建」，合计版本加二 |
| 软废弃字段 | 是 | 无 | 该行置 `deprecated`，列与数据保留 |
| **物理删除字段** | **是（高危）** | **该列历史数据永久丢失** | `DROP COLUMN`，该行置 `dropped`，需二次确认，版本加一。`active` 与 `deprecated` 都可删（两者物理列都在）；`dropped` / `renamed` 返回 `FIELD_NOT_FOUND` |
| 复用 `dropped` / `renamed` 的 Key | 是 | 无 | 清墓碑后 `ADD COLUMN`，建出一列全新的空列，版本加一（见 5.2） |
| 复用 `deprecated` 的 Key | 否 | — | 返回 `FIELD_KEY_RETIRED`。物理列还在，必须先物理删除该列，Key 转为 `dropped` 之后才能按上一行重建 |

四条说明：

**物理删除为什么可以直接做。** ClickHouse 是列式存储，`DROP COLUMN` 只需删除每个 part 中该列的 `.bin` / `.mrk` 文件，**不重写其他列**，属于轻量 mutation，基本瞬时完成。所以代价不是问题，需要守住的只有语义约束——删除后历史数据不可恢复。Key 本身允许重建（见 5.2）：旧数据已经随列一起消失，重建出的是一列全新的空列，不存在“同一列名在不同时间段含义不同”的问题；真正必须挡住的是**物理列还在时的同名重建**，那才会让元数据与物理列脱节，因此 `deprecated` 的 Key 必须先删列才能复用。

**重命名为什么可以不丢数据。** `ALTER TABLE ... RENAME COLUMN a TO b` 是纯元数据操作，数据文件原地保留。因此改名后用新 Key 就能查到该字段的**全部历史数据**，这是比“新增 + 废弃”优越得多的做法。代价只有一个：前端上报代码必须同步改用新 Key，否则旧 Key 会被当成未知字段拒绝。旧 Key 的记录行保留为 `renamed` 状态并指向新 Key，既标明该 Key 已经退役（重建时要先清掉这行墓碑，见 5.2），也保留了变更链可追溯。

**跨类型族改类型为什么必须丢数据。** 理论上 `MODIFY COLUMN` 能做部分转换，但方向上都不可用：`string → boolean` 会因为任意字符串无法转 Bool 而让 mutation 直接失败；`boolean → string` 虽然能跑，但 `Bool` 底层是 `UInt8`，转换结果是 `'0'` / `'1'` 而不是 `'false'` / `'true'`，会静默产出一批语义错误的历史数据；`string → integer` 上一个非数字的历史值就会整条 mutation 失败，`float → integer` 则会静默截断小数。与其提供一个在一半场景下失败、另一半场景下悄悄弄脏数据的功能，不如统一实现为 **`DROP COLUMN` + `ADD COLUMN`（同名，新类型）**：语义单一、结果可预测，代价是该列历史数据清零。由于是物理删除后重建，不存在“同名列在不同时间段含义不同”的问题，因此 Key 允许保持不变。又因为它本就等于「删除 + 重建」，系统**不为它提供接口与入口**：操作者自行走 `DELETE .../fields/:fieldKey` 与 `POST .../fields`（理由见 7.3）。

**`string` ⇄ `enum` 为什么是例外。** 这一对与上面所有组合有本质区别：**它根本不改变列里存的值**。两者的物理类型分别是 `Nullable(String)` 与 `LowCardinality(Nullable(String))`，差别只在字典编码，`MODIFY COLUMN` 是一次无损重写——没有任何一个历史值会失败、会截断、会变形。它们的差别全在**校验强度**上：`enum` 要求上报值命中 `options`，`string` 不要求。所以这条转换的真实含义是「把一个自由文本字段收紧成受控值域」或反过来放开，而不是「换一种数据表示」。

  这也让「先用 `string` 自由收集一段时间，看清真实值域之后再收紧成 `enum`」成为可行路径——这是建表时最难一次拍准的决定，给它一条不丢数据的退路，比要求操作者一开始就想清楚更现实。转换的具体流程、崩溃中间态为什么无害，见 7.3。


### 5.4 字段类型与能力矩阵

**本节是全系统类型能力的唯一真值。** 6.6 的物理类型、8.2 的上报值校验、9.3 的过滤操作符、
9.4 的统计指标、10.3 的字段配置界面、10.6 的查询构建器，全部从这里推导，不得各自维护一份。

#### 5.4.1 六种类型

| `type` | 中文名 | 用途 | 上报 JSON 值 |
|---|---|---|---|
| `string` | 文本 | 自由文本、URL、外部 ID、高基数标识 | `string` |
| `enum` | 枚举 | 取值有限且可枚举：渠道、结果、状态、版本号 | `string`，且必须命中 `options` |
| `boolean` | 布尔 | 是 / 否 | `boolean` |
| `integer` | 整数 | 次数、状态码、金额（分）、时长（毫秒） | `number`，必须是整数 |
| `float` | 小数 | 比率、评分、带小数的度量 | `number`，有限值 |
| `datetime` | 时间 | **业务时间**：下单时间、注册时间、会话开始时间 | `number`，Unix 毫秒时间戳 |

`datetime` 与系统列 `_occurred_at` 不冲突：后者是「这条上报发生的时间」，是全表统一的时间轴；
前者是**业务语义上的另一个时间**，可以早于 `_occurred_at` 很久（今天上报一条三个月前的订单）。
两者都能当趋势查询的时间轴，见 9.4。

#### 5.4.2 能力矩阵

能力是正交的，操作符与统计指标从能力派生：

| 能力 | 派生出什么 |
|---|---|
| `equatable` | 过滤操作符 `eq`、`neq` |
| `enumerable` | 过滤操作符 `in`、`not_in` |
| `ordered` | 过滤操作符 `gt`、`gte`、`lt`、`lte`；统计指标 `min`、`max` |
| `textual` | 过滤操作符 `contains`、`not_contains`、`is_empty`、`is_not_empty` |
| `groupable` | 可作为统计的分组维度（`dimension.kind = "field"`） |
| `uniquable` | 统计指标 `unique`（`uniqExact`） |
| `summable` | 统计指标 `sum`、`avg`、`p50`、`p90`、`p99` |
| `timeAxis` | 可作为趋势查询的时间轴（`dimension.kind = "time"` 的 `axis`） |

| `type` | equatable | enumerable | ordered | textual | groupable | uniquable | summable | timeAxis |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| `string` | ✓ | ✓ | ✗ | ✓ | ✓ | ✓ | ✗ | ✗ |
| `enum` | ✓ | ✓ | ✗ | ✗ | ✓ | ✓ | ✗ | ✗ |
| `boolean` | ✓ | ✗ | ✗ | ✗ | ✓ | ✗ | ✗ | ✗ |
| `integer` | ✓ | ✓ | ✓ | ✗ | ✓ | ✓ | ✓ | ✗ |
| `float` | ✗ | ✗ | ✓ | ✗ | ✗ | ✗ | ✓ | ✗ |
| `datetime` | ✗ | ✗ | ✓ | ✗ | ✗ | ✗ | ✗ | ✓ |

`is_null` / `is_not_null` **对六种类型无条件可用**，不由任何能力控制——「这一行有没有提交该字段」
与字段类型无关，见 6.6 的空值语义。

矩阵里六个 ✗ 是有代价的选择，逐条说明：

- **`float` 没有 `equatable` / `enumerable`。** `price = 0.1` 在二进制浮点下几乎必然查不出行，
  给了这个操作符只会让操作者拿到一个「明明有数据却是空」的结果，而且他没有任何线索知道为什么。
  浮点只给范围比较。需要按精确值筛选的量（金额、版本号、状态码）应当建成 `integer` 或 `enum`。
  **注意这条约束是「浮点不能等值」，不是「数字不能等值」**：`status_code in (500, 502, 504)`、
  `retry_count = 0` 都是最常见的过滤，`integer` 完整保留 `eq` / `in`。
- **`float` / `datetime` 没有 `groupable`。** 连续值直接 `GROUP BY` 会产生近乎行数级别的分组数，
  结果无意义且会打爆查询。`datetime` 要按时间聚合，走 `timeAxis`（`toStartOfDay` 等时间桶）；
  `float` 要看分布，用 `p50` / `p90` / `p99`。
- **`float` 没有 `uniquable`。** 「有多少个不同的浮点数」这个问题的答案取决于浮点表示误差，不可靠。
- **`boolean` 没有 `enumerable`。** 值域只有两个，`in [true]` 与 `eq true` 完全等价，
  多给一个操作符只是让下拉框多一行噪音。
- **`datetime` 没有 `equatable`。** 毫秒精度的等值匹配在实践中永远匹配不到，用范围表达。
- **`enum` 没有 `textual`。** 枚举值是受控的短标识，子串匹配没有意义；想选多个值用 `in`，
  而且前端有现成的选项下拉（见 10.6），比让人手打子串准确得多。

#### 5.4.3 为什么能力由类型反推，而不是逐字段配置

字段定义里**没有**「这个字段允许哪些操作符」之类的开关，能力完全是 `type` 的函数。三条理由：

1. **能力不是偏好，是类型的语义后果。** `float` 不给 `eq` 不是「我们不想给」，是浮点等值本身不可靠；
   `string` 不给 `sum` 是这条 SQL 根本跑不起来。把它做成勾选项，勾错的后果不是「少一个功能」，
   而是**系统给出一个错误的答案**——这比功能缺失严重得多。
2. **给了就要挡两遍。** 字段级的能力表只是一份「建议」，服务端仍然必须按 `type` 再校验一次
   （否则改一行元数据就能绕过），等于同一套约束维护两份，两份迟早不一致。
3. **加类型的成本会翻倍。** 类型反推时，新增一个类型 = 上面那张矩阵加一行；
   逐字段配置时 = 加一行，外加决定所有历史字段的勾选状态怎么迁移。

**能力矩阵由服务端下发，前端不硬编码。** 管理后台通过 `GET /api/admin/field-types`（见 15.8）
取回这张矩阵，查询构建器的操作符下拉、统计页的指标下拉全部照它渲染。
否则前后端各写一份，迟早出现「前端给了 `contains`、后端回 `INVALID_QUERY`」这类只能靠用户报障发现的漂移。

**有一类问题类型答不了：基数。** `user_id`（`string`）拿去做分组维度会很慢，
但这是「划不划算」而不是「合不合法」——同样是 `string` 的 `login_method` 就完全合适。
V1 **不为此增加字段级开关**，改用 9.1 已有的护栏兜底：分组维度强制 Top N、
`max_memory_usage` 超限由 ClickHouse 中止并映射为 `INVALID_QUERY`，最坏结果是一次查询失败，
不会拖垮系统；前端在维度下拉里对 `string` 字段标注「高基数字段分组可能较慢」（见 10.6）。
将来真需要时再加一个**只能减不能加**的护栏位（只允许关掉类型已给的能力，不允许开启没给的），
那时是纯元数据变更，向后兼容。

### 5.5 枚举选项

`enum` 字段的值域是一组选项，一个选项一行存放于 SQLite 的 `collect_field_options`（见 6.4.1）：

```json
{ "value": "wechat", "label": "微信", "status": "active" }
```

- `value`：**实际写进 ClickHouse 列的字符串**，创建后不可修改（改了历史数据就对不上）。
  1–64 UTF-8 字节，不含控制字符，同一字段内唯一
- `label`：管理后台与图表里展示的名称，可以随时修改
- `status`：`active` 允许上报；`disabled` 拒绝新上报，但**历史数据照常查询、照常分组**，
  图例上仍按 `label` 显示

规则：

- 建表或新增字段时，`enum` 必须带**至少一个** `active` 选项，否则该字段收不到任何合法上报。
  非 `enum` 字段带 `options` 返回 `INVALID_FIELD_VALUE`
- 单字段选项数不超过 `maxEnumOptions`（见附录 A）
- **选项只能新增、改 `label`、改顺序、停用、重新启用，不能删除。** 历史数据里可能仍然存在该值，
  删掉选项行等于把那些历史值变成「查得到但没有名字」的裸串。停用已经能达到「不再收新数据」的目的，
  而且是可逆的
- 上报值不在该字段的 `active` 选项内 → `INVALID_FIELD_VALUE`（400），
  错误响应的 `error.expected.options` 带上当前允许的选项列表（受 `maxEnumOptions` 截断），
  与 8.3「字段类错误必须自解释」的既有约定一致

**为什么不用 ClickHouse 的 `Enum` 类型。** `Enum8` / `Enum16` 把值域写进了列的物理类型里，
于是有两个后果：加一个选项要 `ALTER TABLE ... MODIFY COLUMN`，是一次 mutation；
而在这次 ALTER 落地之前，任何携带新值的上报都会被 ClickHouse **直接拒绝写入**。
也就是说「后台加选项」和「前端开始发新值」之间存在一个必须严格排序的窗口，排错了就丢数据。
改用 `LowCardinality(Nullable(String))` + 元数据侧的选项校验之后，
加选项就是写一行 SQLite、清一次缓存，没有 DDL、没有 mutation、没有窗口，
而字典编码带来的存储与 `GROUP BY` 收益一点不少（见 6.6）。
