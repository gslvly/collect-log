## 17. 验收标准

### 17.1 创建和变更

- 管理员可以创建包含全部六种类型字段的数据采集表，物理列类型与 6.6 的映射表逐一对应
  （`enum` 是 `LowCardinality(Nullable(String))`，`integer` 是 `Nullable(Int64)`，
  `datetime` 是 `Nullable(DateTime64(3, 'UTC'))`）。
- `enum` 字段不带选项、或非 `enum` 字段带了选项，建表与新增字段都返回 `INVALID_FIELD_VALUE`。
- 提交选项列表时漏掉一个现存 `value`，返回 `INVALID_FIELD_VALUE` 且**一个选项都没被改动**；
  把它带上并标 `status: "disabled"` 才能停用。停用后该值的历史数据仍可查询、仍出现在分组结果里。
- 新增选项使 `schema_version` 加一，只改选项 `label` 或顺序则版本不变。
- `string → enum` 转换后：历史数据一行不少、不在选项内的历史值仍能查到并参与分组，
  但新上报该值返回 `INVALID_FIELD_VALUE`；`enum → string` 转换后该字段的选项行被清空。
  两个方向之外的任何 `retype` 请求返回 `INVALID_FIELD_TYPE`。
- 手动把某列的物理类型在 `String` 与 `LowCardinality(String)` 之间改掉，重启后 reconcile
  自动 `MODIFY COLUMN` 收敛回元数据声明的类型；改成其它任何类型则只写告警日志、不自动修复。
- 创建成功后返回 `projectId`、`ingestSecret`；管理后台据此拼出可直接运行的 TypeScript 示例。
- 可以新增字段，新字段对历史行表现为 `NULL`。
- 可以软废弃字段，历史数据仍可查询。
- 可以重命名字段，历史数据完整保留在新字段名下，旧 Key 在 `collect_fields` 中留存为 `renamed` 并指向新 Key。
- 可以物理删除字段，需要输入字段 Key 二次确认，且历史数据确实被清除。
- **`deprecated` 的字段同样可以物理删除**：删除后物理列在 `system.columns` 中消失、元数据行变
  `dropped`，此时用同名 Key、新类型重建能成功，且重建出的列对全部历史行都是 `NULL`。
  `dropped` / `renamed` 的字段执行删除返回 `FIELD_NOT_FOUND`；
  `PATCH` / `rename` / `deprecate` 对 `deprecated` 字段一律返回 `FIELD_NOT_FOUND`。
- **不存在修改字段类型的接口与入口**（无 `retype` 路由、无「改类型」按钮）；
  改类型靠操作者自行「物理删除 → 同名新建」两步达成，前端只给提示（见 7.3 / 10.3）。
- `deprecated` 的 Key 无法**直接**重新创建，返回 `FIELD_KEY_RETIRED`，但先物理删除该列之后可以；
  `dropped` / `renamed` 的 Key 可以按 5.2 直接重新创建，建出的是一列全新的空列。
- 创建表单可以从任意一张现有表复制字段定义，回填内容不含 ID、密钥与状态，且回填后可自由增删改；
  提交走的是普通建表请求，服务端不感知模板。
- 复制来的字段照样受全部建表校验约束（Key 格式、保留字、重复 Key、`maxFields`）。
- `active` / `disabled` / `creating` 的表无法删除，返回 `TABLE_STATE_CONFLICT`。
- `archived` / `failed` 的表由 `super_admin` 输入表名二次确认后可以物理删除，
  ClickHouse 物理表、SQLite 元数据行与全部字段墓碑都被清除，`admin` 调用返回 `FORBIDDEN`。
- 删除过程在 `DROP TABLE` 之后崩溃时，重新执行一次删除能干净收尾，且启动 reconcile 会为该表写出告警。

### 17.2 上传

- 业务前端仅通过 HTTP 接口主动上传，签名正确才被接受。
- 签名错误、过期、重放分别返回 `INVALID_SIGNATURE`、`SIGNATURE_EXPIRED`、`REPLAYED_NONCE`。
- 合法请求能写入对应物理表的一行。
- 未知字段、废弃字段、错误类型和缺少必填字段会被拒绝，**错误响应必须指明具体字段名与期望类型**。
- **六种类型的值校验各自生效**：`enum` 收到未登记值、`integer` 收到 `1.5`、`float` 收到 `NaN`
  （手写载荷）、`datetime` 收到窗口外的时间戳，四者都返回 `INVALID_FIELD_VALUE`；
  而类型本身传错（该给数字给了字符串）返回 `INVALID_FIELD_TYPE`。两者不得混用。
- `enum` 值被拒时，`error.expected.options` 列出当前允许的选项，且**不包含已停用的选项**。
- `occurredAt` 超出 `[now-7d, now+5min]` 被拒绝；而 `datetime` 业务字段写入三年前的时间正常成功。
- 接口成功响应表示 ClickHouse 已确认 part 落盘。
- 使用 `sendBeacon` 从跨域页面上报能够成功，不产生 CORS 预检。

### 17.3 查询

- 所有登录用户可以查看所有数据采集表和数据。
- 支持时间范围与六种类型字段的组合筛选。
- **操作符按 5.4.2 的矩阵放行**：对 `float` 字段用 `eq`、对 `enum` 用 `contains`、
  对 `boolean` 用 `in`、对 `datetime` 用 `eq`，四者都返回 `INVALID_QUERY` 且 `message` 说明原因；
  而 `integer` 的 `eq` / `in` 正常工作。
- `GET /api/admin/field-types` 返回的 `operators` / `measures` 与服务端实际放行的完全一致
  （逐类型逐操作符对拍，这条是防前后端漂移的唯一验收点）。
- **统计的两个轴各自生效**：不分组 + `count`、时间维度 + `count`、字段维度 + `count`、
  不分组 + `unique`、时间维度 + `sum`、字段维度 + `p90` 六种组合都返回正确结果；
  能力不匹配的组合（`sum` 一个 `string` 字段、按 `float` 分组）返回 `INVALID_QUERY`。
- 时间维度按 `_occurred_at` 与按某个 `datetime` 业务字段聚合，得到的是**两条不同且都正确**的趋势；
  后者的响应带 `nullAxisRows`，且不做空桶填充。
- 空桶在 `count` / `sum` 下填 `0`，在 `avg` / `min` / `p90` 下填 `null`，且每个桶都带 `rows`。
- 字段维度的结果含 `key: null` 那一档（未提交该字段的行），`share` 之和为 1；
  分组数超过 `limit` 时 `truncated` 为 `true`，且 `count` / `sum` 额外给出 `others`，
  `avg` / `unique` / 分位数不给。
- `integer` 字段在明细与统计响应里是 JSON 数字而非字符串；`datetime` 字段是 ISO 8601 UTC 字符串。
- 按天聚合的结果随传入时区变化而正确变化。
- 查询 API 不接受任意 SQL、物理表名或未注册字段名。
- 明细与导出默认不返回 `deprecated` 字段；传 `includeFields` 后能读回该列的历史数据，
  且列顺序仍按 `field_key` 排序。未知 Key、`dropped` / `renamed` 的 Key、`_` 开头的系统列、
  以及本来就默认选中的 `active` Key 传进 `includeFields` 时，四类各自返回 `INVALID_QUERY`。
- 按 `deprecated` 字段过滤能命中历史行，`statistics` 也能对 `deprecated` 字段求值。
- 翻页途中改变 `includeFields`（或 `filter` / `order` / Schema 版本），旧游标失效并返回 `INVALID_QUERY`。
- 否定类操作符能查出该字段为 `NULL` 的行；`minute` 粒度超过 2 天、`hour` 粒度超过 31 天返回 `INVALID_QUERY`。
- CSV 导出为流式，超过上限时正确截断并标记，表头列集合与明细查询一致。

### 17.4 账户

- `super_admin` 可以创建和删除 `admin` 与 `user`。
- `admin` 可以创建和删除 `user`，但不能创建或删除其他 `admin`。
- 任何角色都不能删除 `super_admin`。
- 禁用最后一个 active `super_admin` 返回 `LAST_SUPER_ADMIN`。
- 登录必须通过图形验证码，同一验证码无法使用两次。
- 所有用户都能修改自己的密码。

### 17.5 并发与恢复（负向用例）

- 并发提交两个同名账户创建请求，只有一个成功，另一个撞 `UNIQUE` 约束并返回 `USERNAME_EXISTS`。
- 并发提交两个新增字段请求，两个字段都成功落地，`schema_version` 连续递增，不发生覆盖丢失。
- 进程被 kill 后重启，SQLite 的 WAL 能正确恢复，不出现半写入的元数据行。
- 同一 `recordId` 重试多次，后台 merge 完成后表中只剩一行。
- 在“物理表已创建、`active` 元数据未写入”之间 kill 进程，重启后 reconcile 自动把表收敛为 `active`。
- 手动在 ClickHouse 中删掉某个已注册的列，重启后 reconcile 自动补回该列并记录日志。
