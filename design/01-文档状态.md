## 1. 文档状态

- 状态：V4.0 设计稿
- 目标：用于指导前后端、SQLite / ClickHouse 表结构和管理后台的实现
- **V3 相对 V2 的变更：管理元数据从 ClickHouse 迁到 SQLite**，采集数据仍在 ClickHouse。
  动机是元数据需要事务与唯一约束，而 ClickHouse 两者都没有；顺带把持久化收敛到单一根目录，
  降低上线配置成本。业务语义、上报协议、字段模型、错误码一律未变。
- **V3.1 相对 V3 的变更：砍掉 `tableId`，全系统只保留一个公开 ID `projectId`。**
  原来两个 ID 严格一一对应，除了带来命名混淆和一次多余的一致性校验之外没有收益。
  一个项目就是一张采集表。随之上报路由改为 `/api/ingest/v1/projects/:projectId/rows`，
  错误码 `INVALID_TABLE_ID` 改名为 `INVALID_PROJECT_ID`（唯一一处错误码改名）。
  同时把「元数据缓存必须有容量上限且不缓存空结果」写进 13 的硬性要求。
- **V3.1 修订（2026-08-28）**：新增错误码 `INVALID_FIELD_KEY`（400），承接原先复用
  `INVALID_JSON` 的「字段 Key 不符合 5.2 正则」一类错误；并把 15.3 删表与 15.4 字段路由的
  请求 / 响应字段名写进 15，此前它们只在实现里存在。
  同日第二次修订：**`dropped` / `renamed` 的字段 Key 改为允许重新创建**（清墓碑再建，
  全程不触碰物理列与历史数据，见 5.2 / 7.2 / 7.3），`deprecated` 仍不可复用（V3.2 起改为「先物理删除该列再复用」）；
  Key 冲突的错误码随之分成 `FIELD_KEY_EXISTS`（正被占用）与 `FIELD_KEY_RETIRED`（已软废弃）。
  同时补上 7.3 重命名的 DDL 幂等与 7.4 对「重命名被打断」中间态的收敛规则。
  同日第三次修订：**砍掉 `POST .../fields/:fieldKey/retype` 路由，同时取消管理后台的「改类型」入口**——
  字段类型不可修改，前端只提示「请先删除该列，再新建同名列」，由操作者自行走
  「物理删除 + 同名新建」两个独立操作（见 5.2 / 5.3 / 7.3 / 10.3 / 10.4 / 15.4）。
  理由是单条路由在 DDL 与元数据之间崩溃时会静默回滚成旧类型。不新增也不改名任何错误码。
  除此之外协议未变。
- **V3.2 相对 V3.1 的变更（2026-08-29）：解开「软废弃是单向死路」这个结。**
  V3.1 之前 `deprecated` 字段写不进（8.2 拒收）、查不出（9.1 白名单只认 `active`）、
  列删不掉（物理删除只接受 `active`）、Key 也拿不回来，软废弃实际上是一个只能进不能出的终态。
  本次按两条改动收口，**协议其余部分未变**：
  1. **`deprecated` 字段可以物理删除**：删除的前置条件从「仅 `active`」放宽到「`active` 或
     `deprecated`」——这两种状态下物理列都还在，`DROP COLUMN` 才有意义（见 5.3 / 7.3 / 15.4）。
     删完 Key 落到 `dropped` 墓碑上，按 5.2 就能以新类型重建，`FIELD_KEY_RETIRED` 从「永久占用」
     变成「先删列再复用」。
  2. **落实 7.3 早已写下的「历史查询可以显式选择废弃字段」**：`query` / `export` 新增可选
     `includeFields`，`filter` 与 `statistics.field` 直接放行 `deprecated` 字段（见 9.1 / 15.6）。
     此前这句话在实现里没有任何载体。
  同时修正 5.3 变更规则表里与 5.2 直接矛盾的「复用已退役字段 Key｜否｜永久禁止」一行、
  其后两段正文的相关表述，以及 6.4 的「退役即 tombstone」一条（原文写「只要存在任何一行就不能再创建」，
  与 5.2 允许清墓碑重建相悖）；6.4 的字段状态表补上「可查询 / 可物理删除 / Key 可重建」三列，
  四种状态的完整能力现在一眼可查。并把此前只记在 `AGENTS.md`「对 DESIGN 的授权补充」里的四条收进正文：
  错误码 `ROUTE_NOT_FOUND`（404）与 `UNSUPPORTED_MEDIA_TYPE`（415）进 8.3 的表、
  `/healthz` 的 3 秒探测超时进 12.5、`captchaRateLimitPerIp` 进附录 A。
  另补记实现中已经生效但设计稿漏写的接口与限额：`GET .../row-count`、表详情响应的字段集合、
  趋势查询按粒度收紧的时间跨度、9.3 若干操作符的精确语义。
- **V4.0 相对 V3.2 的变更（2026-08-30）：重做字段类型系统与统计模型。** 这是 V3 以来第一次
  改动业务语义，影响面覆盖建表、上报、查询、统计与管理后台，因此升主版本号。四条改动：

  1. **字段类型从两种扩到六种**：`string` / `enum` / `boolean` / `integer` / `float` / `datetime`
     （见 5.4.1、6.6）。此前只有字符串和布尔，数值只能存成字符串，导致求和、平均、分位数、
     范围过滤全部无法表达，而这些恰好是埋点数据最主要的统计需求。
  2. **能力由类型反推，不逐字段配置**（见 5.4.2、5.4.3）。每种类型声明一组正交能力，
     过滤操作符与统计指标全部从能力派生；服务端通过新接口 `GET /api/admin/field-types`（15.8）
     把这张矩阵下发给前端，前后端只有一份真值。**字段定义里没有任何能力开关**——
     能力是类型的语义后果而非偏好，勾错的后果是系统给出错误答案。
     一个直接结论：`float` 不提供等值与 `in`（浮点等值不可靠），而 `integer` 完整提供。
  3. **统计接口从枚举 `metric` 换成 `dimension` × `measure` 两轴模型**（见 9.4、15.6）。
     原来的 `total` / `trend` / `unique` / `group` / `boolean_ratio` 全部是它的特例，
     同时补上了枚举法表达不了的「每天 GMV」「各渠道 p90 耗时」「按业务时间看趋势」。
     响应新增 `totals` / `others` / `truncated` / `rows`，口径见 9.4.4。
  4. **新增枚举选项表 `collect_field_options`**（见 6.4.1、5.5）与两条字段路由
     （`PUT .../options`、`POST .../retype`，见 15.4）。枚举值域是元数据校验，
     物理上是 `LowCardinality(Nullable(String))`，**不用 ClickHouse `Enum`**——
     后者加选项要 ALTER，且 ALTER 落地前携带新值的上报会被直接拒收（理由见 5.5）。

  连带的两处规则调整：**`string` ⇄ `enum` 成为全系统唯一允许的类型转换**（物理同族、转换无损，
  见 5.3 / 7.3），此前「类型一律不可修改」的铁律对这一对不再成立，其余组合仍然禁止；
  7.4 的 reconcile 增加**物理类型漂移检查**，只自动收敛 `String` ⇄ `LowCardinality(String)`，
  其余不一致只写告警。

  **新增唯一一个错误码 `INVALID_FIELD_VALUE`（400）**，覆盖「形状正确但取值不合法」，
  与管形状的 `INVALID_FIELD_TYPE` 分工（见 8.2.1、8.3）。除它之外未新增或改名任何错误码。
- 系统定位：面向前端主动调用接口的动态数据采集与统计系统
