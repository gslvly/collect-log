## 1. 文档状态

- 状态：V3.1 设计稿
- 目标：用于指导前后端、SQLite / ClickHouse 表结构和管理后台的实现
- **V3 相对 V2 的变更：管理元数据从 ClickHouse 迁到 SQLite**，采集数据仍在 ClickHouse。
  动机是元数据需要事务与唯一约束，而 ClickHouse 两者都没有；顺带把持久化收敛到单一根目录，
  降低上线配置成本。业务语义、上报协议、字段模型、错误码一律未变。
- **V3.1 相对 V3 的变更：砍掉 `tableId`，全系统只保留一个公开 ID `projectId`。**
  原来两个 ID 严格一一对应，除了带来命名混淆和一次多余的一致性校验之外没有收益。
  一个项目就是一张采集表。随之上报路由改为 `/api/ingest/v1/projects/:projectId/rows`，
  错误码 `INVALID_TABLE_ID` 改名为 `INVALID_PROJECT_ID`（唯一一处错误码改名）。
  同时把「元数据缓存必须有容量上限且不缓存空结果」写进 13 的硬性要求。
- **V3.1 修订（2026-08-28）**：新增错误码 `INVALID_FIELD_KEY`（400），承接原先复用
  `INVALID_JSON` 的「字段 Key 不符合 5.2 正则」一类错误；并把 15.3 删表与 15.4 字段路由的
  请求 / 响应字段名写进 15，此前它们只在实现里存在。
  同日第二次修订：**`dropped` / `renamed` 的字段 Key 改为允许重新创建**（清墓碑再建，
  全程不触碰物理列与历史数据，见 5.2 / 7.2 / 7.3），`deprecated` 仍不可复用；
  Key 冲突的错误码随之分成 `FIELD_KEY_EXISTS`（正被占用）与 `FIELD_KEY_RETIRED`（已软废弃）。
  同时补上 7.3 重命名的 DDL 幂等与 7.4 对「重命名被打断」中间态的收敛规则。
  同日第三次修订：**砍掉 `POST .../fields/:fieldKey/retype` 路由，同时取消管理后台的「改类型」入口**——
  字段类型不可修改，前端只提示「请先删除该列，再新建同名列」，由操作者自行走
  「物理删除 + 同名新建」两个独立操作（见 5.2 / 5.3 / 7.3 / 10.3 / 10.4 / 15.4）。
  理由是单条路由在 DDL 与元数据之间崩溃时会静默回滚成旧类型。不新增也不改名任何错误码。
  除此之外协议未变。
- 系统定位：面向前端主动调用接口的动态数据采集与统计系统
