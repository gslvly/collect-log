## 9. 查询与统计

### 9.1 查询原则

- 管理前端不能提交原始 SQL。
- Node 根据当前 Schema 的物理字段白名单生成 SQL，字段名只能来自白名单。
- 所有查询必须包含时间范围，且不超过配置的最大跨度。
- 限制返回行数、查询耗时和并发数（见附录 A）。
- 明细列表使用游标分页，不使用大 OFFSET。游标是 `(_occurred_at, _record_id)` 的 keyset，编码为不透明 Base64 串。
  游标里带一个**查询指纹**：`sha256(canonicalJson({ projectId, range, filter, includeFields, order, schemaVersion }))`
  取前 16 位。翻页途中改动其中任何一项（包括中途加列、Schema 变了），指纹对不上，
  直接返回 `INVALID_QUERY` 要求重新从第一页开始，而不是接着一个语义已经变了的游标往下翻。
- 采集数据查询一律不加 `FINAL`（见 2.1 与 8.5）。SQLite 侧不存在这个问题。
- 明细查询**不使用 `SELECT *`**，由服务端按当前 Schema 展开显式列名。这样宽表加列后查询开销不会失控，且能自动隐藏已废弃字段。
- **显式选择已废弃字段（7.3 那句「历史查询可以显式选择」的载体）**。默认列集合只含 `active` 字段，
  要看废弃字段的历史数据，在 `query` / `export` 的请求体里传可选的 `includeFields: string[]`（默认 `[]`）：
  - 只接受当前 `deprecated` 的 Key。未知 Key、`dropped` / `renamed` 的 Key（名下已无物理列）、
    `_` 开头的系统列（本来就无条件返回）、以及本来就默认选中的 `active` Key，一律 `INVALID_QUERY`
    并在 `message` 里说明是哪一类。宁可报错也不静默忽略——静默忽略会让操作者以为“这列确实没数据”。
  - 最终列集合 = `active` 字段 + `includeFields`，**合并后仍按 `field_key` 排序**，
    与下一条「默认顺序即服务端返回顺序」保持一致。CSV 导出用同一套列集合（见 9.5）。
  - `filter` 条件与 `statistics` 的 `dimension.field` / `measure.field` / `axis` **直接放行 `deprecated` 字段**，不需要经过 `includeFields`：
    这两处字段名本来就是操作者显式写出来的，已经满足「显式选择」；`dropped` / `renamed` / 未知字段
    / 系统列仍然是 `INVALID_QUERY`。
  - 服务端为此要读取全部字段行（含墓碑），不能复用只含 `active` 的表结构缓存——
    该缓存是上报热路径的数据来源，不为低频的管理查询改形状。
- **明细结果表格支持拖动列顺序、隐藏列、显示列**（2026-08-28 拍板）。纯前端状态，不影响服务端返回的列集合，
  也不落后端持久化，本地记忆即可。与上面「服务端按 Schema 展开列名」是两层：后端决定**能返回哪些列**，
  前端这里决定**从中挑哪些列、以什么顺序展示**。默认全选、默认顺序即服务端返回顺序（`ORDER BY field_key`）。
- **返回值的编码口径**（六种类型，明细 / 统计 / 导出三处一致）：`string` / `enum` 返回字符串，
  `boolean` 返回 `true` / `false`，`integer` / `float` 返回 JSON 数字，
  `datetime` 与系统列 `_occurred_at` / `_received_at` 一样返回 **ISO 8601 UTC 字符串**
  （`2026-08-30T04:00:00.000Z`），未提交一律 `null`。两条必须显式设置的 ClickHouse 输出选项：
  - `output_format_json_quote_64bit_integers = 0`。ClickHouse 默认把 64 位整数**输出成字符串**
    以免 JS 丢精度，但本系统的 `integer` 在上报时就已经卡死在 `±(2^53-1)`（见 8.2.1），
    不存在精度问题，而带引号的数字会让前端拿到 `"42"`，图表和排序全部错位。
  - `datetime` 列不要直接吐 ClickHouse 默认的 `'2026-08-30 04:00:00.000'` 格式：
    它既没有时区标记也不是 ISO，前端 `new Date()` 解析出来会按本地时区偏移。
- **并发闸**：查询与导出各有独立的并发上限（附录 A 的 `maxConcurrent`），超出时**立即拒绝**，
  返回 `RATE_LIMITED`（429），不排队等待——排队只会把压力从 ClickHouse 挪到 Node 的内存里，
  而调用方看到的仍然是超时。
- **ClickHouse 故障分三类映射**，不要一律 500：连接不上 / 探测超时 → `CLICKHOUSE_UNAVAILABLE`（503）；
  查询超过 `max_execution_time`、`max_memory_usage`、`max_result_rows` 等限额被 CH 主动中止 →
  `INVALID_QUERY`（400，这是调用方要求太多，改小范围就能成功）；其余未知异常 → `INTERNAL_ERROR`（500）。

### 9.2 时区处理

物理存储一律 UTC。但所有**按时间粒度聚合**的接口必须接收时区参数，否则国内用户的“今天”会从早上 8 点开始：

```sql
-- 错误：固定 UTC
SELECT toDate(_occurred_at) AS bucket, count() ...

-- 正确：时区由前端传入
SELECT toStartOfDay(_occurred_at, {tz:String}) AS bucket, count() ...
```

- 按天：`toStartOfDay(_occurred_at, {tz:String})`
- 按小时：`toStartOfHour(_occurred_at, {tz:String})`（`+05:30` 这类半小时时区必须传，不能省）
- 按分钟：`toStartOfMinute(_occurred_at)`

前端传 IANA 时区名（如 `Asia/Shanghai`），由 Pinia 中的全局设置统一提供，默认取浏览器 `Intl.DateTimeFormat().resolvedOptions().timeZone`。

### 9.3 字段操作符

**操作符可用性由字段 `type` 经 5.4.2 的能力矩阵推导，本节不另立一张表。**
服务端按矩阵校验，前端按 `GET /api/admin/field-types`（见 15.8）下发的同一份矩阵渲染下拉。
用了没有对应能力的操作符 → `INVALID_QUERY`，`message` 写明「`float` 字段不支持 `eq`」这类具体原因，
而不是笼统的「非法操作符」。

| 操作符 | 需要的能力 | 值 | 生成的 SQL |
|---|---|---|---|
| `eq` | `equatable` | 单值 | `` `f` = {v} `` |
| `neq` | `equatable` | 单值 | ``(`f` IS NULL OR `f` != {v})`` |
| `in` | `enumerable` | 非空数组 | `` `f` IN ({v1}, {v2}, …) `` |
| `not_in` | `enumerable` | 非空数组 | ``(`f` IS NULL OR `f` NOT IN (…))`` |
| `gt` `gte` `lt` `lte` | `ordered` | 单值 | `` `f` > {v} `` 等，**不包 `NULL`** |
| `contains` | `textual` | 单值 | `position(`f`, {v:String}) > 0` |
| `not_contains` | `textual` | 单值 | ``(`f` IS NULL OR position(`f`, {v:String}) = 0)`` |
| `is_empty` | `textual` | 无 | `` `f` = '' `` |
| `is_not_empty` | `textual` | 无 | ``(`f` IS NOT NULL AND `f` != '')`` |
| `is_null` | 无条件可用 | 无 | `` `f` IS NULL `` |
| `is_not_null` | 无条件可用 | 无 | `` `f` IS NOT NULL `` |

值的 JSON 类型必须与字段 `type` 相容，规则与上报侧同源（见 8.2.1）：`string` / `enum` 收字符串、
`boolean` 收布尔、`integer` / `float` / `datetime` 收数字（`datetime` 是 Unix 毫秒）。
不相容返回 `INVALID_QUERY`。**`enum` 的过滤值不校验是否在 `options` 内**——
历史数据里可能存在已停用甚至从未登记过的值（见 7.3 的类型转换），
查不到自己写的值和查不到本来就存在的数据，后者的代价大得多。

条件支持嵌套 `AND` 和 `OR`，但限制最大条件数量和嵌套层级（见附录 A）。
`in` / `not_in` 的**数组元素个数逐个计入** `maxConditions`，否则一个条件就能塞进上万个值。

四条精确语义，实现时不能走样：

- **否定类操作符必须显式包住 `NULL`**：`neq` / `not_in` / `not_contains` 一律生成
  ``(`f` IS NULL OR <否定条件>)``。ClickHouse 的三值逻辑会让 `f != 'a'` 把 `f IS NULL` 的行整个吞掉，
  于是操作者选「不等于 A」却看不到那些根本没提交该字段的行——而这些行显然也「不等于 A」。
- **范围比较相反，一律不包 `NULL`。** `lt` / `lte` 看起来像「否定」，但「未提交」不小于任何值，
  把 `NULL` 行塞进 `cost_seconds < 1` 的结果里是错的。`is_not_empty` 同理：
  它的语义是「有内容」而不是「不等于空串」，因此是唯一一个不包 `NULL` 的否定形操作符。
  这条与上一条的分界是「否定一个取值」还是「断言一个取值」，不是看操作符名字里有没有 `not`。
- **子串匹配用 `position(col, {v:String}) > 0`，不用 `LIKE`**，免掉转义用户输入里 `%` 和 `_` 的出错面。
  大小写敏感。
- **过滤字段白名单**只认当前 `active` 与 `deprecated` 的字段（见 9.1），`_` 开头的系统列一律拒绝
  （时间范围已由 `range` 单独处理），`dropped` / `renamed` 与未知字段等同未知 → `INVALID_QUERY`。

### 9.4 统计模型

统计接口只有**两个正交的轴**：**按什么分组**（`dimension`）和**统计什么**（`measure`）。
所有统计需求都是这两个轴的组合，接口不再枚举「总数 / 趋势 / 去重 / 分组 / 占比」这类固定组合。

```json
{
  "range": { "start": 1756000000000, "end": 1756600000000 },
  "tz": "Asia/Shanghai",
  "filter": { "op": "and", "conditions": [] },
  "dimension": { "kind": "time", "axis": "_occurred_at", "granularity": "day" },
  "measure": { "fn": "sum", "field": "pay_amount" }
}
```

**为什么不是枚举 metric。** 枚举法下，「按天看上报量」和「按天看 GMV」是两个不同的 metric，
「按渠道看数量」和「按渠道看 p90 耗时」又是两个——组合数是两个轴的乘积，
每加一种维度或一种聚合函数，要新增的 metric 数量都是乘法级的，而它们的 SQL 只差一个聚合表达式。
拆成两个轴之后，加一个聚合函数就是加一行 SQL 模板，加一种维度同理。

#### 9.4.1 dimension：按什么分组

| `kind` | 参数 | 含义 |
|---|---|---|
| 省略 / `null` | — | 不分组，返回单个值 |
| `"time"` | `axis`、`granularity` | 按时间桶分组，即趋势 |
| `"field"` | `field`、`limit?` | 按字段取值分组，即分布 / Top N |

- `axis` 取 `_occurred_at`（默认）或任意具备 `timeAxis` 能力的字段（即 `datetime` 类型，见 5.4.2）。
  前者是「这条数据什么时候报上来的」，后者是「这条数据描述的业务事件什么时候发生的」——
  同一批数据按两条轴画出来的趋势是不同的，且都合理（见 5.4.1）。
- `granularity` 取 `minute` / `hour` / `day`，按 9.2 的时区规则生成时间桶，**必须**配合 `tz`。
  按粒度收紧时间跨度的规则见附录 A。
- `field` 必须具备 `groupable` 能力。`limit` 是 Top N，默认 `defaultGroupLimit`，
  上限 `maxGroupLimit`（见附录 A）。
- `kind: "time"` **不接受 `limit`**：桶数已经被「跨度 × 粒度」限死，再给一个 limit 只会
  截出一段没头没尾的时间轴。

#### 9.4.2 measure：统计什么

| `fn` | 需要的能力 | 聚合表达式 |
|---|---|---|
| `count` | 不带 `field` | `count()` |
| `unique` | `uniquable` | `uniqExact(f)` |
| `sum` | `summable` | `sum(f)` |
| `avg` | `summable` | `avg(f)` |
| `min` / `max` | `ordered` | `min(f)` / `max(f)` |
| `p50` / `p90` / `p99` | `summable` | `quantile(0.5)(f)` 等 |

- `count` 之外的 `fn` 都必须带 `field`；`count` 带了 `field` 返回 `INVALID_QUERY`
  （想要「该字段非空的行数」请用 `unique` 或加一个 `is_not_null` 过滤条件，不要让 `count` 有两种含义）。
- 能力不匹配返回 `INVALID_QUERY`，`message` 指出是哪个字段的哪种类型不支持哪个 `fn`。
- **聚合一律跳过 `NULL`**（ClickHouse 语义）。因此 `avg` 的分母是该字段非 `NULL` 的行数，
  不是命中的总行数——响应里的 `totals.rows` 与每行的 `rows` 就是为了让这个口径可见（见 9.4.4）。
- `min` / `max` 对 `datetime` 返回 ISO 8601 字符串，对 `integer` / `float` 返回数字。

`dimension` 与 `measure` 的组合覆盖了全部既有统计需求，也覆盖了枚举法表达不了的那些：

| 想看的东西 | `dimension` | `measure` |
|---|---|---|
| 总上报量 | 省略 | `count` |
| 上报趋势 | `time` | `count` |
| 独立用户数 | 省略 | `unique(user_id)` |
| 登录方式分布 | `field(login_method)` | `count` |
| 记住我占比 | `field(remember_me)` | `count`（`share` 自动给出） |
| **每天 GMV** | `time` | `sum(pay_amount)` |
| **各渠道 p90 耗时** | `field(channel)` | `p90(cost_ms)` |
| **每小时独立用户数** | `time(hour)` | `unique(user_id)` |
| **按业务时间看注册趋势** | `time(axis=registered_at)` | `count` |
| **各渠道客单价** | `field(channel)` | `avg(pay_amount)` |

#### 9.4.3 生成的 SQL

无维度：

```sql
SELECT sum(`pay_amount`) AS value, count() AS rows
FROM data.collect_a8f31c
WHERE `_occurred_at` >= {start:DateTime64(3, 'UTC')}
  AND `_occurred_at` <  {end:DateTime64(3, 'UTC')};
```

时间维度：

```sql
SELECT toStartOfDay(`_occurred_at`, {tz:String}) AS bucket,
       sum(`pay_amount`)                         AS value,
       count()                                   AS rows
FROM data.collect_a8f31c
WHERE `_occurred_at` >= {start:DateTime64(3, 'UTC')}
  AND `_occurred_at` <  {end:DateTime64(3, 'UTC')}
GROUP BY bucket
ORDER BY bucket
WITH FILL FROM toStartOfDay({start:DateTime64(3, 'UTC')}, {tz:String})
             TO toStartOfDay({end:DateTime64(3, 'UTC')}, {tz:String})
           STEP INTERVAL 1 DAY;
```

字段维度：

```sql
SELECT `login_method` AS key,
       count()        AS value,
       count()        AS rows
FROM data.collect_a8f31c
WHERE `_occurred_at` >= {start:DateTime64(3, 'UTC')}
  AND `_occurred_at` <  {end:DateTime64(3, 'UTC')}
GROUP BY key
    WITH TOTALS
ORDER BY value DESC, key ASC
LIMIT {group_limit:UInt32};
```

四条实现约束：

- **`WITH TOTALS` 而不是第二条查询。** 分组结果需要一个总计来算占比、来算「其它」那一档，
  `WITH TOTALS` 让 ClickHouse 在同一次扫描里带回不受 `LIMIT` 影响的全量总计，
  省掉一次往返，也避免两条查询之间数据发生变化导致占比加起来不等于 1。
- **空桶补零只在 `axis = _occurred_at` 时做。** 那时桶的起止范围可以由 `range` 直接推出，
  `WITH FILL` 的 `FROM` / `TO` 有确定的值。业务时间轴不补：`range` 约束的是 `_occurred_at`，
  业务时间可以落在范围之外的任何地方，起止无从推断，硬填会画出一条长度不可预料的时间轴。
- **`rows` 列必须始终带上。** 它有两个用途：一是区分「`WITH FILL` 填出来的空桶」与
  「真实值就是 0 的桶」——`WITH FILL` 填的是列类型的默认值 `0`，
  对 `count` / `sum` 恰好正确，但对 `avg` / `min` / `p90` 是错的，
  服务端必须把 `rows = 0` 的桶的 `value` 改写成 `null` 再返回；
  二是让前端能显示样本量，一个由 3 行数据算出来的 p99 和由 300 万行算出来的 p99 不该长得一样。
- **时间轴是业务字段时补一条 `axis IS NOT NULL`**，否则未提交该字段的行会挤进一个假桶。
  被排除的行数在响应里以 `nullAxisRows` 返回——不告诉操作者，趋势图的总量就会和总数卡片对不上，
  而他找不到原因。

#### 9.4.4 响应

```json
{
  "dimension": "field",
  "measure": { "fn": "count" },
  "rows": [
    { "key": "sms",      "value": 8123, "rows": 8123, "share": 0.62 },
    { "key": "password", "value": 4210, "rows": 4210, "share": 0.32 },
    { "key": null,       "value": 780,  "rows": 780,  "share": 0.06 }
  ],
  "totals": { "value": 13113, "rows": 13113 },
  "others": { "value": 0 },
  "truncated": false
}
```

- `key`：时间维度是 ISO 8601 UTC 字符串（桶的起点），字段维度是该字段的取值。
  **`key` 为 `null` 表示「未提交该字段」的那一组**，它必须作为正常的一档返回，
  不能悄悄丢掉——「有多少行压根没报这个字段」经常正是要看的东西。
  `enum` 字段的取值由前端按 `options` 的 `label` 渲染（含已停用选项，见 5.5）。
- `share`：仅 `fn = count` 时给出，等于 `value / totals.value`。布尔字段的真假占比因此不需要
  单独的接口——它就是 `dimension.kind = "field"` 落在一个 `boolean` 字段上的普通结果。
- `others`：Top N 之外那些组的合计，**仅 `fn ∈ {count, sum}` 时给出**，
  等于 `totals.value - Σ rows[].value`。`avg` / `unique` / 分位数不可加，
  剩余部分无法由已知结果推出，这时只给 `truncated: true`，前端不得自行拼一个「其它」。
- `truncated`：分组数超过 `limit` 时为 `true`（用 `LIMIT n + 1` 探测）。
- `nullAxisRows`：仅当时间轴是业务字段时出现，见 9.4.3 第四条。
- 无维度时 `rows` 只有一个元素且没有 `key`，`dimension` 为 `null`。

**`deprecated` 字段在 `dimension.field`、`measure.field`、`axis` 三处直接放行**，
与 9.1 里 `filter` 的规则一致：这些字段名都是操作者显式写出来的，已经满足「显式选择」。
`dropped` / `renamed` / 未知字段 / `_` 开头的系统列（`_occurred_at` 作为 `axis` 时除外）
仍然是 `INVALID_QUERY`。

### 9.5 CSV 导出

采用**流式导出**，不在 Node 内存中缓冲整个结果集：

1. 以 `FORMAT CSVWithNames` 向 ClickHouse 发起查询。列集合与明细查询同一套规则
   （系统列 + `active` 字段 + `includeFields`，按 `field_key` 排序，见 9.1），
   表头因此直接来自 SELECT 的列名，服务端不另外拼一份。
2. 将 CH 返回的可读流直接 pipe 到 HTTP 响应，配合 `Content-Disposition: attachment`。
3. 设置服务端硬上限（见附录 A）；超限时截断并在最后一行追加注释说明，同时在响应头 `X-Export-Truncated: 1` 标记。
4. 导出查询使用 `ch_readonly` 账户，并附带 `max_execution_time` 与 `max_result_rows` 限制。

### 9.6 数据量增长后的优化预留

数据量增长后，可以为高频过滤字段增加数据跳数索引，为固定仪表盘增加小时或天级物化聚合表。V1 不提前创建这些结构。
